# A/B：我们 vs ffmpeg（2026-11-06）

**这份表回答一个问题**：同一份源、同一组参数，我们的 `.mp4` 链路（VC-1/WMV2 解码 →
MPEG-4 Part 2 编码 → MP4 封装）与 `ffmpeg -c:v mpeg4` 相比，**速度**和**产物质量**
各是什么水平。

原始数据在 [`ab-ffmpeg-20261106.tsv`](ab-ffmpeg-20261106.tsv)，由
[`tools/ab_ffmpeg.py`](../tools/ab_ffmpeg.py) 生成（可重跑）。

## 口径（这比数字本身重要）

| 项 | 取值 | 为什么 |
|---|---|---|
| 输入 | 两侧吃**同一个源文件** | 输入编码对两侧的解码成本是同一份，不会偏向谁 |
| 量化 | `v2v -q 6` vs `ffmpeg -q:v 6` | 同 qscale。**注意这不是同码率**，见下面「怎么读」 |
| GOP | `-g 12` / `-g 12` | 同上 |
| B 帧 | ffmpeg 侧 `-bf 0` | 本仓编码器没有 B 帧，放开等于换一个编码器在比 |
| 线程 | **两侧都 1** | ffmpeg 的 VC-1 解码默认开帧级多线程，不钉住就是「比机器」 |
| 音频 | 两侧都关 | AAC 的质量口径与视频不是一把尺子，混在一张表里会误读 |
| 速度 | 3 次取**最快** | 抖动只会让它变慢，不会变快 |
| 质量 | 产物 vs **源**，**按帧号配对** | 见「陷阱一」 |

机器：Apple M3（8 核）/ aarch64 / release / 量的时候 load 3.90 3.32 3.27。

## 语料

6 段 3 秒短片，全部由 `ffmpeg` 现造（**不进仓库**：真素材一律不入库，脚本重跑即可）：

| 名字 | 内容 | 编码 |
|---|---|---|
| `real_720p` | 真内容（一段动画 OP 的第 10–13 秒） | VC-1 1280×720（`-c copy`，无损切） |
| `real_360p` | 同一段的 640×360 缩版 | WMV2 |
| `synth_720p` / `synth_360p` | `testsrc2`（有运动、有细节的合成画面） | WMV2 |
| `static_360p` | `gradients`（近静止，最容易压） | WMV2 |
| `noise_360p` | 满幅随机噪声（最难压） | WMV2 |

| `real_360p` | 90 | 397 | 153 | **2.60×** | 845 | 820 | 1.03× | **41.03** | 40.32 | **0.9839** | 0.9778 |

| `synth_360p` | 90 | 225 | 114 | **1.98×** | 472 | 567 | 0.83× | 42.93 | **44.17** | 0.9897 | **0.9922** |
| `static_360p` | 90 | 218 | 78 | 2.78× | 88 | 60 | 1.46× | **53.71** | 51.55 | **0.9956** | 0.9927 |

## 怎么读

**1. 速度：慢 2–4.3 倍，且分辨率越高差距越大。**
360p 是 1.98–3.08×，720p 是 2.92–4.34×。720p 那两行最值得注意：解码（VC-1）与编码
（MPEG-4）的成本都随分辨率涨，而 ffmpeg 那边两者都高度优化过。

**2. 质量：真内容上我们**更好**，合成/噪声上更差。**
- 真内容（`real_720p` / `real_360p`）：PSNR **+0.6 ~ +0.7 dB**、SSIM **+0.6 ~ +1.5 个点**，
  代价是体积 1.03–1.12×。
- 近静止（`static_360p`）：PSNR **+2.2 dB**、SSIM +0.3 个点，但体积 **1.46×** ——
  这一段本来就几乎不耗码率，绝对差只有 28 KB。
- **噪声（`noise_360p`）：PSNR 低 4.2 dB**，体积小 19%。这是明确的短板：随机噪声
  在频域是平的，没有「该省的地方」，我们的量化/判决在这种情况下把码率压得太狠。

**3. 「同 qscale」不等于「同码率」，更不等于「同质量」。**
体积比从 0.79× 到 1.46× 都有。所以这张表能回答「同样的旋钮下谁更好」，
**不能**回答「同码率下谁更好」—— 后者要跑一遍码率对齐（`--video-bitrate` vs `-b:v`），
还没做。

## 两个测量陷阱（都真的踩到了）

**陷阱一：`ffmpeg -lavfi psnr` 按时间戳配对，不按帧号。**
我们的 `.mp4` 声明的 fps / timebase 是从源时间戳推出来的，与源未必一致。差几帧它照样
「比完给个数」，只是那个数被系统性拉低。实测同一份 `real_720p` 产物：

| 口径 | PSNR-Y |
|---|---|
| `ffmpeg -lavfi psnr`（按时间戳） | **23.66 dB** |
| 按帧号对齐（`tools/psnr.py`） | **39.57 dB** |

**差 16 dB。** 如果只用滤镜口径，结论会从「我们略好」翻转成「我们差得离谱」。
所以 `ab_ffmpeg.py` 先把三条流解成**裸 yuv**（没有时间戳），再让 psnr/ssim 滤镜比。

**陷阱二：ffmpeg 默认多线程。**
第一版没给 `-threads 1`，量出来 720p 是 4.99×；钉住单线程后是 4.34×。
差的那 13% 不是实现差距，是「它用了 4 个核」。

## 复现

```bash
# 造语料（真素材路径自己给；合成的那几段不需要素材）
S=/path/to/a/real.wmv
ffmpeg -ss 10 -t 3 -i "$S" -c copy -y /tmp/v2v_corpus/real_720p.wmv
ffmpeg -ss 10 -t 3 -i "$S" -vf scale=640:360 -c:v wmv2 -b:v 3M -an -y /tmp/v2v_corpus/real_360p.wmv
ffmpeg -f lavfi -i testsrc2=size=1280x720:rate=30:duration=3 -c:v wmv2 -b:v 4M -an -y /tmp/v2v_corpus/synth_720p.wmv
ffmpeg -f lavfi -i testsrc2=size=640x360:rate=30:duration=3 -c:v wmv2 -b:v 2M -an -y /tmp/v2v_corpus/synth_360p.wmv
ffmpeg -f lavfi -i "gradients=size=640x360:rate=30:duration=3" -c:v wmv2 -b:v 2M -an -y /tmp/v2v_corpus/static_360p.wmv
ffmpeg -f lavfi -i "nullsrc=size=640x360:rate=30:duration=3,geq=random(1)*255:128:128" \
       -c:v wmv2 -b:v 2M -an -y /tmp/v2v_corpus/noise_360p.wmv

cargo build --release -p v2v-cli
tools/ab_ffmpeg.py --reps 3 --out /tmp/ab.tsv /tmp/v2v_corpus/*.wmv
```

   是量化判决把高频全砍了，还是代价函数对平坦频谱估得不对。
2. **速度**：720p 4.34×。瓶颈在解码还是编码，`v2v bench` 已经能把两者分开量。
