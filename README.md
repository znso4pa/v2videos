# v2videos

用 **Rust** 研究「视频之间的编码格式转换」—— 也就是把一种视频（**容器 + 视频编码 + 音频编码**）  
转成另一种，整条链路的每一段都拿出来看看：在纯 Rust 里能做到什么、边界在哪、代价是什么。

> 名字里的 `v2v` = **v**ideo **to** **v**ideo。

## 转换链路

一次转换拆成四段，研究也按这四段走：

```text
         ┌─ 解封装 ──► 解码 ──► 像素域 / 采样域 ──► 编码 ──► 封装 ─┐
输入 ────┤   demux      decode     (YUV / PCM)        encode   mux   ├──── 输出
         └──────────────────────────────────────────────────────────┘
```

中间那层「像素域 / 采样域」是关键的解耦点：两端互相不认识，只认中间那份裸数据。

## 目录

```text
crates/
  container 各容器共用的数据模型（流 / 格式 / 样本）—— 零依赖
  asf      ASF（.wmv / .wma）解封装 + **封装** —— 纯 std
  avi      AVI（RIFF）解封装
  msmpeg4  MS-MPEG-4 v3（MP43）/ WMV1 / WMV2 解码（I / P + **IntraX8**）+ MP43 编码（I / P，含运动估计与帧内/帧间判决）
           **兼共享数值内核**：位读写器 / FDCT / IDCT / FFT / VLC 表 —— mp4v、aac、wma 都从这里取
  wma      WMA v1/v2 音频解码（帧头 / LSP 指数 / 系数 / IMDCT）
  vc1      VC-1（**WMV3**）解码：Simple/Main profile、渐进、I/P —— 目前只到**帧头 + 位平面**
  mp4v     MPEG-4 Part 2（mp4v）**编码**：I / P + 码率控制
  aac      **AAC-LC 编码**：MDCT（长/短窗）+ TNS + Huffman 码本 + 码率控制
  mp4      MP4 / ISOBMFF **封装**（ftyp / mdat / moov；音频 AAC 或 PCM）
  cli      `v2v` 命令行：**批量转码**（解封装 → 解码 → 编码 → 封装）
tools/
  gen_tables.py     H.263 / MPEG-4 Part 2 的 VLC / 反量化表（附自检：前缀无关、Kraft 和、逐码往返）
  check_tables.py   用**第二个独立来源**核对 msmpeg4 的表
  gen_aac_tables.py AAC 的 Huffman 码表 / 频带表
  gen_wma_tables.py WMA 解码的码表 / 频率表
  gen_vc1_tables.py VC-1 的位平面 VLC / 量化表 / 枚举常量（`vc1data.c`、`vc1_vlc_data.h`）
  gen_intrax8_tables.py IntraX8 的 AC/DC/方向码表与量化矩阵（`intrax8huf.h` 等）
  ffmpeg_src.py     从上游文件头**原样抽出**版权行（各生成器共用，见 NOTICE）
  gen_notice.py     生成根目录的 NOTICE
```

⚠️ **各生成器的默认源目录 `/tmp/ffsize/ffmpeg-7.1` 是作者的本地路径**，
第三方 clone 里不存在。要重新生成表，先自己准备一份 FFmpeg 7.1 源码
（<https://ffmpeg.org/download.html>），再用参数指过去：
各生成器都是**位置参数**（`python3 tools/gen_tables.py <ffmpeg 源码目录>`），
`gen_wma_tables.py` 用 `--src <ffmpeg>/libavcodec`。

## 构建与测试

```bash
cargo build
cargo test        # 单元测试 + 不依赖样本的集成测试
```

**与 `ffmpeg` / `ffprobe` 的交叉验证**是本仓的判据：解码结果逐像素对、封装字段逐字段对、  
编码出来的流交回 ffmpeg 解。这些测试需要一个真样本，用环境变量指路；**缺样本时打  
`SKIP` 并通过**，所以新 clone 下来 `cargo test` 直接就能跑：

```bash
V2V_ASF_SAMPLE=/path/to/sample.wmv cargo test

# 整段样本逐帧对账（最重的一条，默认标了 #[ignore]）：
V2V_ASF_SAMPLE=/path/to/sample.wmv cargo test --release -- --ignored
```

按「一段一段啃」推进。已经落到代码上的：

| -------- | ----------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **解封装**  | ASF / WMV（`v2v-asf`）、AVI（`v2v-avi`）                                                                         | 与 `ffprobe` 逐字段对：轨道、尺寸、包数、关键帧数                                                                  |
| **解码**   | MS-MPEG-4 v3（**MP43**）、**WMV1**（WMV7）与 **WMV2**（WMV8）：I 帧 + P 帧（skip、MV 预测、半像素运动补偿、帧间残差）。三版共用骨架，**分叉在帧头与几处版本常量**上：`pict_type` 位宽、ext header 的位置、变长/定长的第三 escape、`ff_wmv1_scantable` 那套扫描表、DC 预测的平手方向与缩放（`scale != 8` 时走 `FASTDIV`，对负数**向下取整**）。**WMV2 另有一整套**：逐宏块 skip 表（4 种粒度）、按 qscale 挑的 CBP 表、`mspel` 四抽头半像素 + 逐宏块 `hshift`、**ABT**（4×8 / 8×4，含自己的扫描表与第二个半块）、**环路滤波**（逐宏块就地滤，skip 宏块也要滤）、以及 **IntraX8**（`j_type` —— 一个按 8×8 块走的内帧子解码器：12 种空间预测 + 自己的环路滤波 + 自己的熵编码，`extradata` 的能力位置位时**每个 I 帧**都归它） | 与 `ffmpeg` **逐像素**对：MP43 / WMV1 / WMV2 各自的真样本**每一帧最大差 0**（WMV2 **六份样本共 24321 帧**，其中 **126 帧走 IntraX8**；含 `mspel`、ABT、环路滤波、边缘复制那些分支） |

| **编码**   | MP43 **I 帧 + P 帧**：正向 DCT + 量化 + DC / RL 熵编码、运动估计（整像素粗搜 + 半像素细化）、skip 宏块                                    | 编出来的 I+P 序列交给 `ffmpeg` 解，与自己的解码器**逐像素一致**                                                       |
| **编码**   | MPEG-4 Part 2（`v2v-mp4v`）**I 帧 + P 帧**：DC / AC 预测（逐宏块比位数择优）、运动估计（**三起点菱形搜索 + 时间预测**，半像素细化）、中值 MV 预测、skip 宏块、逐宏块帧内/帧间判决；`--video-bitrate` 时**逐帧调 qscale** 的码率控制 | 编出来的流交给 `ffmpeg` 解，真样本 **44.8 dB**（同 qscale 下 ffmpeg 自己的 mpeg4 是 43.6 dB）；**视频载荷比全 I 帧小 2.3 倍**；码率控制实测命中目标（371→373、621→618 kbps） |
| **音频直通** | 转换时原样搬音频轨（ASF 多流复用）                                                                                         | 真样本整条音轨：输出音频与源**逐样本 0 差异**（整轨字节完全一致）                                           |

| **封装**   | ASF 写（`.wmv`，单视频流）：**多载荷打包** + **Simple Index**（每 1 秒一个 seek 槽） | `ffprobe` 认；自己解封装字节一致；ffmpeg 解出来的像素与我们的解码器**逐位一致**；真样本载荷占文件 **89%**（改前 24%）、体积小 3.8 倍；`ffmpeg -ss` 能读出我们写的索引 |
| **封装**   | MP4 / ISOBMFF 写（`v2v-mp4`，视频 `mp4v`；音频 `mp4a`+`esds`（AAC）或 `sowt` PCM）                                     | 真样本 mp4v 轨的 `stsz`/`stts`/`stss`/`stco` 与 ffmpeg **逐项相同**、逐帧 MD5 一致；PCM 轨原样往返；AAC 轨 ffmpeg 解得开 |

**两条输出路**（`v2v convert`，默认 `.wmv`）：

```bash
# .wmv：视频重编码成 MP43，音频**直通**（零损失），会做 PSNR 校验
v2v convert in.wmv -o out/

# .mp4：视频重编码成 MPEG-4 Part 2（-g 给 GOP，默认 250 帧 ≈ 10 秒；0 = 全 I 帧），
#       音频 WMA → PCM → **AAC-LC**（--pcm 可退回未压缩 PCM）
v2v convert --mp4 -g 12 in.wmv -o out/
```

**为什么 `.mp4` 必须重编码**：MP4 / 3GP 容器**不收 MP43**（`mp4`/`3gp`/`3g2` 三个 muxer 都报  
`codec not currently supported in container`），`mov` 收但是单向街 —— 写出来的东西 ffmpeg  
自己读不回来。WMA 同理。所以 `.wmv → .mp4` 这条路上视频必须过一遍 MPEG-4 Part 2 编码器，  
音频必须解成 PCM 再重编码（默认 AAC，`--pcm` 则是原封不动的 `sowt`）。

**还没做（解码侧）**：**WMV9 / VC-1 的宏块层**（`v2v-vc1` 现在只到**帧头 + 位平面**，见下一段）。
MP41 / MP42 的帧头已经按版本分叉了，但 MB 层还没写
（要走 H.263 的 MCBPC 表）—— 输入被明确拒绝，不会静默出错。

**VC-1 走到哪一步**：新 crate `v2v-vc1` 已经能解**序列头**（容器 extradata 里的 `STRUCT_C`）、
**帧头**（I/P）与帧头里的**位平面**（逐宏块跳过标志那类整帧位图，7 种编码 + 差分算子）。
判据是外部 oracle：`ffmpeg -debug pict` 的逐帧日志 —— 真样本 1920×1080 **3719 帧逐帧对齐**
（`pict_type` 与两张位平面的 `(imode, invert)` 全同；位平面紧跟帧头标量，差一位就变形，
所以这等价于「帧头解完时位游标一位不差」）。**宏块层、逆变换、运动补偿、环路滤波还没写** ——
所以它现在还不能解出像素，也没接进 CLI。范围限定在 **Main profile / 渐进 / I/P**：
Advanced profile、B 帧、隔行遇到就明确报错。

**还没做（编码侧）**：MPEG-4 Part 2 的 **B 帧**与 8×8 运动补偿、AAC 的 **PNS** 与**逐带** M/S
掩码（现在只做逐帧 —— 全部带一起选；TNS 只覆盖长窗）、WMA **编码器**（现在只能解）、
MP4 的分片 / `co64`、其他容器与编解码器。

## 与 `ffmpeg` 的全面对表（2026-10-16 实测）

**口径**（这几条不一起看就会读出错误结论）：

- 真样本、**同一台机器、背靠背 A/B**；机器空闲时量（有负载时绝对值明显变慢，所以只看比值）
- `ffmpeg 9.0.1`（本机），`-threads 1`；**我们的视频编码本来就是单线程**（`--threads` 只作用于 AAC 声道并行）
- 「倍数」= 我们 ÷ ffmpeg，**大于 1 = 我们慢**
- ⚠️ **同一个 `-qscale` ≠ 同一个码率**：两边的量化器实现不同，同 q 下体积差 ±20% —— 每行都带体积
- ⚠️ **PSNR 是自己解码后逐帧算的**（`ffmpeg -lavfi psnr` 在**时间戳不齐**的两个输入上会按帧率重采样、
  于是错位比较：同一份产物它能给出恒定 24 dB 的假数）—— 见文末「踩过的坑」

### 1. 解码速度（只解视频、单线程；`crates/msmpeg4/tests/decode_bench.rs`）

| 样本 | 编码 | 尺寸 | 帧数 | 我们 ms/帧 | ffmpeg ms/帧 | 倍数 |
|---|---|---|---|---|---|---|
| 真样本 A | MP43 | 320×240 | 5201 | 0.12 | 0.07 | **1.92×** |
| 真样本 C | MP43 | 160×120 | 153 | 0.03 | 0.20 | **1.49×** |
| 真样本 E | WMV1 | 360×240 | 1379 | 0.08 | 0.06 | **1.91×** |
| 真样本 D | WMV1 | 512×512 | 249 | 0.12 | 0.15 | **2.80×** |
| 真样本 F | WMV2 | 176×144 | 767 | 0.07 | 0.10 | **1.06×** |
| 真样本 G | WMV2 | 320×240 | 898 | 0.14 | 0.16 | **1.11×** |
| 真样本 H | WMV2 | 640×360 | 9541 | 0.36 | 0.35 | **1.03×** |
| 真样本 I | WMV2 | 1280×720 | 600 | 2.35 | 2.48 | **0.98×** |
| 真样本 J | WMV2 | 1280×720 | 600 | 1.45 | 1.37 | **1.13×** |

⚠️ ffmpeg 每跑一次要付**进程启动**（20–30 ms），帧少的样本里它占大半 —— 所以上表是
「两边都减掉解 1 帧那一趟」的**纯解码吞吐**（`(我们 N − 我们 1) / (ffmpeg N − ffmpeg 1)`）。
不减的话，153 帧那行会算出「我们快 4 倍」这种纯属分母灌水的数。
⚠️ **720p 那两行只比了前 600 帧**（不是口径变了，是**内存**：对账测试把两边的帧都摊在内存里，
720p 整段约 11 GB，实测把 swap 打满 —— 见 `TODO.md`）。帧数少了靠「去启动」那一步兜住。
**解码正确性**：三档编码的真样本都是**逐像素最大差 0**（见上面「状态」那节）。
（这张表比提速前**快了 1.75–2.67×**：位读取器从逐位读改成字宽、VLC 加 9 位快表、
列变换 4 通道一批（读的时候不再拷块）、RL 符号编进快表、几处内层写法 ——
**WMV2 那三行已经追平 ffmpeg**（1.03–1.11×），MP43 还慢 1.5–1.9 倍。
再往下要动 IDCT 的 SIMD intrinsics，那会引入本仓目前没有的 `unsafe`，见 `TODO.md`。）

### 2. 端到端转码（`v2v convert` vs `ffmpeg`，同 qscale、同帧数上限）

| 样本 | 路 | 帧数（我们/ff） | 我们 ms/帧 | ffmpeg ms/帧 | 倍数 | 体积 | PSNR 我们 | PSNR ffmpeg |
|---|---|---|---|---|---|---|---|---|
| 真样本 E（WMV1 360×240） | `.mp4` | 1379 / 1379 | 1.52 | 0.74 | **2.05×** | 1.01× | **44.6** | 43.0 |
| 真样本 H（WMV2 640×360） | `.mp4` | 500 / 500 | 5.32 | 0.82 | **6.50×** | 1.16× | **40.3** | 38.2 |
| 真样本 A（MP43 320×240） | `.mp4` | 500 / 500 | 1.63 | 0.60 | **2.71×** | 0.99× | **44.9** | 44.0 |
| 真样本 F（WMV2 176×144） | `.mp4` | 767 / 768 | 0.64 | 0.32 | **1.95×** | 1.07× | **41.8** | 40.3 |
| 真样本 A（CFR 源） | `.wmv` | 500 / 500 | 2.54 | 0.20 | **12.6×** | 1.02× | **44.9** | 44.1 |
| 真样本 E（VFR 源） | `.wmv` | 1379 / 1568 | 2.95 | 0.22 | **11.8×** | 0.94× | 44.2 | 不可比 |
| 真样本 H（VFR 源） | `.wmv` | 500 / 500 | 9.19 | 0.68 | **13.6×** | 1.26× | 40.3 | 不可比 |
| 真样本 F（VFR 源） | `.wmv` | 767 / 861 | 1.13 | 0.11 | **9.1×** | 1.21× | 41.8 | 不可比 |
| 真样本 I（WMV2 1280×720） | `.mp4` | 500 / 500 | 43.32 | 3.14 | **13.8×** | 1.09× | **50.2** | 49.1 |
| 真样本 J（WMV2 1280×720） | `.mp4` | 500 / 500 | 25.54 | 1.44 | **17.7×** | 1.03× | **55.1** | 53.9 |
| 真样本 I（CFR 源） | `.wmv` | 500 / 500 | 65.70 | 4.44 | **14.8×** | 0.87× | 48.5 | **49.6** |
| 真样本 J（CFR 源） | `.wmv` | 500 / 500 | 31.27 | 2.18 | **14.3×** | 0.80× | 54.1 | **54.6** |

读法：

- **`.wmv` 路的「不可比」不是我们挑的**：`msmpeg4v3` 编码器**拒绝重复时间戳**，ffmpeg 只能把
  **变帧率（VFR）的源转成恒定帧率** —— 补帧、重写时间轴，帧数甚至从 1379 变 1568。
  帧都对不上，逐帧比 PSNR 就没有意义（拿它硬比会得到 11–17 dB 这种假数）。
  **我们保留源的时间轴**（帧数与时间戳都不动），所以只有 CFR 源（真样本 A）两边能直接比。
  这本身是**我们比 ffmpeg 强的一点**：这条路上它改写了时间轴，我们没改。
- **瓶颈是编码，不是解码**：解码慢 1.3–3.1×（上表），编码慢 **9–14×**（`.wmv`）与 **2–6.5×**（`.mp4`）。
  （`.wmv` 那侧已经过一轮提速：运动搜索改三层宽搜 + 两笔逐字节不变的内层改动，见 `TODO.md`；
  实测时间与质量都不降、`.mp4` 路用的 mp4v 没动，所以上面 `.mp4` 那几行仍是原值。）
- **质量**：小尺寸那四条能比的行里我们**每一条都更高**（+0.9 ～ +1.6 dB），体积 0.97–1.16×。
  但**到了 720p 分成两种走法**：`.mp4` 路仍然更高（+1.09 / +1.25 dB，体积 1.03–1.09×），
  而 `.wmv`（MP43）路**更低**（−1.09 / −0.53 dB）—— 只是它同时更小（0.80–0.87×）。
  补一个 q 扫描（400 帧）看趋势：**同 q 下 ffmpeg 每一档都更好**，
  且**码率越高差距越大**（真样本 I：q=2 −4.01 dB、q=3 −1.41、q=4 −0.53；
  真样本 J：−2.33 / −0.52 / −0.32）—— 我们的 MP43 编码器**高码率那一段质量明显弱**，
  体积优势也换不回来。这是下一步编码器该看的地方（`TODO.md`）。
- **这一轮之后我们这边更快了**：按上面的调研做了两笔**输出逐字节不变**的改动
  （SAD 重塑 + AC 量化改倒数乘法），背靠背 A/B 实测 720p `.mp4` **−10.6%**、`.wmv` −3.2%。
  所以上表「我们 ms/帧」那列是优化**前**量的，偏保守；**倍数**那列基本不动
  （`TODO.md` 有完整记录与复核口径）。
- **720p 上端到端更慢**：`.mp4` 路 13.8–17.7×（小样本上是 2.0–6.5×）——
  我们的 mp4v 是纯标量，代价随像素线性涨，而 ffmpeg 那条路吃 SIMD；`.wmv` 路 14.3–14.8×（与小样本的 11.8–13.6× 同档）。

### 3. 率-质量扫描（`.mp4` 路，真样本 E，两边都 `-threads 1`）

| 编码 | qscale | 体积 | 整体 PSNR | 逐帧中位 |
|---|---|---|---|---|
| 我们 mp4v | 3 | 4789K | **48.7 dB** | 48.8 |
| ffmpeg mpeg4 | 3 | 4656K | 47.6 dB | 47.6 |
| 我们 mp4v | 6 | 3069K | **44.6 dB** | 45.0 |
| ffmpeg mpeg4 | 6 | 2955K | 43.0 dB | 43.4 |
| 我们 mp4v | 10 | 2077K | **41.0 dB** | 41.8 |
| ffmpeg mpeg4 | 10 | 1992K | 39.6 dB | 39.9 |
| 我们 mp4v | 16 | 1490K | **37.7 dB** | 38.3 |
| ffmpeg mpeg4 | 16 | 1528K | 36.4 dB | 36.3 |

同体积下我们**每个点都高 1.0–1.6 dB**，而且两边都是单调的（这很重要：不单调说明量法有问题，
不是编码器有问题 —— 第一版量法就是坏的）。

### 4. 音频（AAC-LC 128 kbps，对「源解出的 WMA PCM」比 SNR）

| 样本 | 我们 | ffmpeg | 差 |
|---|---|---|---|
| 真样本 E（立体声） | **22.57 dB** | 16.63 dB | **+5.9** |
| 真样本 A（立体声） | **12.40 dB** | 11.99 dB | **+0.4** |
| 真样本 F（单声道） | **41.48 dB** | 37.50 dB | **+4.0** |

⚠️ **口径**：先用 FFT 互相关**搜对齐**再算 SNR —— AAC 有编码器延迟（ffmpeg 的 AAC 实测比源
**超前 2048 样本**），不搜对齐会量出不可能的负数。我们那条轨对齐偏移是 **0**（不写 priming 帧、
也不写 edit list）。上表是**完整长度**的对比：拿 `-n` 截过的产物比会把两边截在不同位置，数字作废。

### 5. 这套量法踩过的坑（写下来免得重踩）

1. **`ffmpeg -lavfi psnr` 会在时间戳不齐时错位**：同一份产物，它给 24 dB、自己解码逐帧算是 49 dB。
   症状是「**PSNR 不随 qscale 变**」（体积差 3× 而 PSNR 恒定）—— 见到这种数就该怀疑量法。
2. **同 qscale ≠ 同码率**：不带体积的 PSNR 对比会得出错误结论（第一版就是这么错的）。
3. **变帧率的源上 ffmpeg 会补帧**：帧数对不上就不能逐帧比（`ms/帧` 才是公平的速度口径）。
4. **音频不能用 `-n` 截**：`v2v -n N` 会把音频一起截，ffmpeg 的 `-frames:v` 不会 —— 两边截在不同位置。
5. **对齐搜索别用暴力**：±20000 偏移 × 900 万样本在 Python 里是分钟级；FFT 互相关几秒就出。
6. **`ffmpeg` 的日志默认会折叠重复行**（`AV_LOG_SKIP_REPEATED`）：拿 `-debug` 日志当 oracle
   时，连续几十行一模一样的输出会被压成「Last message repeated N times」—— 日志成了**子集**，
   不报错，只让逐帧对账**整体错位**（VC-1 那条：3719 帧只剩 3525 行，看着像「第 10 帧起全错」）。
   要用 `-loglevel repeat+debug`。另外读入阶段的**探测解码器**也在打同一批日志，得按
   上下文地址把它那几行摘掉。

AAC 编码器**低码率已经反超 ffmpeg**（64k：**7.94 vs 6.37 dB**），中码率基本持平
（128k：13.17 vs 13.74 dB，而且我们少用 6% 的字节），**高码率仍明显落后**
（256k：18.86 vs 24.42 dB —— 不过 ffmpeg 那一档还多花了 2.5% 的比特）。
高码率的差距来自 `plan_group` 的**全局量化下界**
（最细只能到「整帧峰值」决定的那一档，频谱动态范围大时安静频带吃亏）与
「按带乘权重」式的心理声学模型（真正的**按带分配比特**还没做）。
**这条差距收窄了一点**：escape 重建漏符号那个 bug 修好后（见上），256k 上实测
**+0.29 dB**（同一套量法）；**每帧预算原来还按声道平均分**（M/S 下 `S` 空时那半份
白扔 —— 单声道源复制成两轨的老 `.wmv` 上，总码率只能到目标的一半）也改成按需要分，
真样本 128k **+0.42**、256k +0.15 dB。细节在 `TODO.md`（本地）。

## 能力矩阵

**格式 × 方向 × 状态。** 三态：✅ 已实现（有对账测试钉着）、❌ 未实现（附原因）。
「已知差异」单列在最后 —— 「能跑」和「和 ffmpeg 一样」是两件事，分开说。

### 容器

| 容器                      | 解封装 | 封装 | 边界与原因                                                                                   |
| ----------------------- | --- | --- | --------------------------------------------------------------------------------------- |
| **ASF**（`.wmv` / `.wma`） | ✅   | ✅   | 只做单视频流 + 单音频流（音频**直通**，不重编码）；不做加密、多视频轨、非标准的纠错标志                                        |
| **AVI**（RIFF）           | ✅   | ❌   | 只读 —— `.wmv → .avi` 没人要，写它没有用例。不认 OpenDML（`AVIX` 分块 / `indx`），遇到明确报 `Unsupported` 而不是假装支持 |
| **MP4** / ISOBMFF        | ❌   | ✅   | 只写 —— 仓里的 ISOBMFF **读取器**都在测试里（手搓的），不进产物。不做编辑列表（`edts`/`elst`）、分片 MP4、`co64`（> 4 GiB）、H.265/AV1 的 sample entry |

### 视频编码

| 编码                       | 解码        | 编码        | 边界与原因                                                                        |
| ------------------------ | --------- | --------- | ---------------------------------------------------------------------------- |
| **MP43**（MS-MPEG-4 v3）   | ✅ I / P   | ✅ I / P   | 这是 `.wmv` 的主编码。解码有 AC 预测那条路（ffmpeg 编的流里 `ac_pred` 恒 0，靠翻位测试覆盖）                 |
| **WMV1**（WMV7）           | ✅ I / P   | ❌         | 与 MP43 共用 MB 层，分叉在帧头、扫描表、DC 预测/缩放表（见「状态」那行）。**不做错误隐藏** —— 首帧不是 I 帧的流直接报错，ffmpeg 会拿垃圾当参考硬解 |
| **WMV2**（WMV8）           | ✅ I/P + IntraX8 | ❌         | 帧头与 MB 层是另一套（`wmv2dec.c`）。比 WMV1 多：`parse_mb_skip`（4 种跳帧类型）、按 qscale 挑的 CBP 表、`mspel` 四抽头半像素 + `hshift`、**ABT**（4×8 / 8×4）、**环路滤波**、它自己那份 8×8 IDCT，以及 **IntraX8**（`j_type`，按 8×8 块走的内帧子解码器，WMV2 与 VC-1 共用 —— 见 `intrax8.rs`） |
| **WMV9 / VC-1**          | 🚧 帧头      | ❌         | **ffmpeg 里根本没有 VC-1/wmv3 编码器**（只有解码器），想要 WMV9 得另找路子。解码侧 `v2v-vc1` 已落地**序列头 + 帧头 + 位平面**（Main profile / 渐进 / I/P，3719 帧逐帧对齐 `ffmpeg -debug pict`）；**宏块层及以下还没写**，所以还不能出像素 |
| **MPEG-4 Part 2**（`mp4v`） | ❌         | ✅ I / P   | 解码不做（进 MP4 之后交给播放器）。编码缺 B 帧、8×8 运动补偿、`dquant`、resync marker、数据分割             |
| **H.264 / AVC**          | ❌         | ❌         | 不在范围内（LGPL 侧链不了 x264，见「许可证」）                                                  |

### 音频编码

| 编码                  | 解码      | 编码      | 边界与原因                                                          |
| ------------------- | ------- | ------- | -------------------------------------------------------------- |
| **WMA v1 / v2**     | ✅       | ❌       | 不写编码器 —— 往 `.wma` 走时音频是**直通**，重编码没有用例                            |
| **AAC-LC**          | ❌       | ✅       | 不写解码器（`ffmpeg` 解得开就够了）。编码缺 **PNS**（噪声替换）、**IS**（强度立体声）、LTP |
| **PCM**（`sowt`）     | ✅（直通）  | ✅（直通）  | 未压缩，进出都是原字节                                                    |

### 已知与 `ffmpeg` 的差异

| 项 | 对比口径 | 我们 vs `ffmpeg` |
| --- | --- | --- |
| **MP43 解码** | 整段真样本逐像素 | **最大差 0** |
| **WMA 解码** | 整轨对 ffmpeg 的 PCM，逐样本 | 最大差 **2**（v1）/ **3**（v2）—— 满量程 32768 |
| **音频直通** | 整条音轨 | **逐字节一致** |
| **ASF 封装** | ffmpeg 解我们写的 `.wmv` | 像素与我们的解码器**逐位一致** |
| **MP43 编码** | 不比 PSNR —— 比的是「两个解码器解得一样」 | 逐像素一致 |
| **`mp4v` 编码** | 同 qscale，真样本 PSNR | **44.8 dB** vs 43.6 dB → **+1.2 dB** |
| **AAC 编码 @64k** | 同目标码率，对 ffmpeg 解出的 WMA PCM 比 SNR | **+1.57 dB** |
| **AAC 编码 @128k** | 同上 | **−0.57 dB**（且少 6% 字节） |
| **AAC 编码 @256k** | 同上 | **−5.56 dB** |

**一句话**：解码侧是「逐像素 / 逐字节」，编码侧只有 AAC 在高码率上落后
（原因见上面「状态」一节里 `plan_group` 那段）。

⚠️ **还有一个口径差异不是质量、是策略**：`--video-bitrate` 给目标码率时，我们**打满**它，
而 ffmpeg 的 mpeg4 会**欠**（实测目标 500k 它只花 370k）。所以「文件更大」在多数情况下
是**我们把码率用满了**，不是编码器效率低 —— 同码率比才是公平比法。

## 命令行

```bash
cargo run --release -p v2v-cli -- convert <输入.wmv>... -o <输出目录> [-q 6] [-g 250] [-n 100]
cargo run --release -p v2v-cli -- convert --mp4 <输入.wmv>... -o <输出目录> [-q 6] [-g 12] [--fps 25]
cargo run --release -p v2v-cli -- convert --mp4 --video-bitrate 500k <输入.wmv>... -o <输出目录>
```

`.mp4` 的音频默认 AAC：`--aac-bitrate 128000` 给目标码率，`--pcm` 退回未压缩 `sowt`，
`--no-ms` 关掉 M/S 立体声（只为对比测量）。
`--threads N` 给并行度（默认 1）：视频按 **GOP** 并行（每块起一个全新编码器 —— 所以
`>1` 时产物与单线程**不完全相同**：每个 GOP 的第一个 P 帧少一个搜索起点、码控从头收敛；
`1` 则跨 GOP 连续，与老行为逐字节相同）；音频按**帧**并行（批内连续分块）与**声道**并行。
两者的线程数都封顶到可用并行度。

**输入编码**：`MP43`、`WMV1`（WMV7）与 `WMV2`（WMV8）—— 其余 MS-MPEG-4 版本会**明确报错
且不留输出文件**，不会静默按错的语法解。
`--video-bitrate` 只对 `.mp4` 有效：给了它就按目标码率**逐帧调 qscale**（`-q` 退化成起步值），
转完会报**实际**码率；不传就还是按固定的 `-q` 编。

批量：一个输入失败不影响其他。默认（`.wmv`）转完会把输出**解码回来**与源帧比 PSNR；  
`--mp4` 不做这个校验 —— 我们只有 `mp4v` 编码器、没有解码器（那条路的正确性由  
`crates/mp4v/tests/ffmpeg_roundtrip.rs` 钉着）。

输入容器按**魔数**自动认（`ASF` / `AVI`，不看扩展名），视频轨支持 **MP43 / WMV1 / WMV2**；  
别的容器 / codec 会明确报「不支持」，不静默跳过。

## 路线与分支策略

这个项目绕不开一个两难：**要么保 FFI / 结构清晰**（强调可复用性、流畅性、可监督性——  
每一段清晰可查、可单独替换、能当库嵌进别的应用），**要么追齐 ffmpeg 的性能**  
（SIMD / 手写内核 / 定点化，复杂度与可维护性代价都大）。

**我们的取舍：在 Android 上拿到最完整构建是第一优先级，性能暂时让路。** 落到分支上：

- **`main` = 可扩展性**。新能力、新格式、结构改良进 main；性能敏感的实现  
  允许「正确但慢」——先把语义钉对，再谈快。
- **性能改动进按类型归类的专门分支**（同类型改动进同一分支，便于跟进与随时改动）：  
  `perf/encode`（编码提速）、`perf/decode`（解码提速）、`perf/tables`（码表改良）。
- 性能分支**保持短命**：定期 rebase、验证过（输出字节不变）就合回 main——  
  永远不合并的性能优化等于没有。

**实测的位置**：见下面「与 ffmpeg 的全面对表」——**编码慢、解码接近**，
音频那条链已经打平。曾经在**一份小样本**上量到过「端到端只慢 1.33 倍」，
那是短样本上启动开销与音频占比把视频编码那一段盖住了的产物，**不能代表一般素材**。

**五笔大的都是「本该便宜却没便宜」**（每一笔的判据都是**产物 MD5 不变**，
除非注明；每笔前后的数都记在 `TODO.md`）：

① **变换是 O(N²)**：AAC 的前向 MDCT 与 WMA 的 IMDCT 原来都逐点调 `cos()`。
AAC 那半先治（`预旋转 → 2N 点 FFT → 后旋转`：单编 20 秒 13.85 → 2.81 s，**4.9×**）；
WMA 这半走同一条路（`n` 点 DCT-IV 折成三段对称 + 一次 `2n` 点 FFT）：
**WMA 解码 1.73 → 0.10 s（约 17×）**。FFT 住在共享内核 `v2v-msmpeg4`，aac 与 wma 调同一份。
（WMA 这条是**唯一**不是逐字节的：PCM 里 550/716800 个样本差 ±1 LSB —— 旧版逐项舍 f32、
新版 f64 累完收一次，**新版更准**。）

② **MP43 解码的运动补偿每块都在做无用功**：`edge_emu` 每块一次 `vec!` 分配 + 逐像素
两次 `clamp`，`put_pixels` 靠逐像素闭包算地址。改成栈 scratch + 三段切片 + 相位分开写。

③ **运动估计把同一个候选反复求值**：菱形每走一步、三个起点各走一遍、±2 补搜、半像素
细化 —— 而 SAD 只取决于候选与参考帧。加一张**直接映射 + 代号**的记忆表（256 槽，
每宏块换一代、不清表）：**视频路径 ×1.30**。

④ **两个编码器的运动估计各写了一份**：MP43 那半每个候选都「先 `mc_luma16` 搬进缓冲
再求和」（两趟内存流量），mp4v 那半早就融合成一趟 —— 合成共享内核里的 `sad_luma16`；
顺带去掉 MP43 ME 里那个占了整条 `.wmv` 链路 **12%** 的 `HashSet` 去重：
**`.wmv` 路径 ×1.23**。

⑤ **AAC 的失真评估算了 11 次、还白算位数**：11 本码本只有 **6 个不同的封顶值**
（1,1,2,2,4,4,7,7,12,12,16），而失真只取决于封顶值 → 算 6 次就够；「位数」那一半本来
就是白算的（`band_cost` 只看失真，位数由 `write_band` 写位流时自己算）：**AAC ×1.7**。

**外加一个真 bug**：AAC 的代价模型里 escape 那一路的反量化漏了符号（位流没错 ——
escape 码本无符号、符号位单独发）。负系数的误差于是被估成 `(|c|+rec)²` 量级，编码器
系统性避开 escape、把大系数逼去撞 `maxval ≤ 16` 的普通码本。修好后 **256k 上 +0.289 dB**
（64k / 128k 几乎不变 —— 低码率下 sf 预算本来就主导）。

**下一个靶子**：视频那 81% —— 运动估计（13%）、共享 DCT、位写入与封装；
再往前就是**分块并行**（按 I 帧切、固定 qscale 下逐字节不变）这一轴。
加速的路子（哪些做过了、哪些试过又撤了、每步前后量到的数）都在 `TODO.md`（本地）里。

## 许可证

**LGPL-2.1-or-later**，见 [LICENSE](LICENSE)。

选 LGPL 的**原因很直接：编解码需要的 VLC / 反量化 / Huffman 码表**  
（`crates/msmpeg4/src/tables.rs`、`crates/mp4v/src/tables.rs`、`crates/aac/src/tables.rs`、  
`crates/wma/src/tables.rs`）是从 FFmpeg 的数据文件读出来的（同为 LGPL-2.1-or-later）。  
表本身是 H.263 / MPEG-4 Part 2 / MPEG-4 Audio / WMA 的**格式定义**、与实现无关，  
也可以换数据源重新生成（`tools/` 下的生成器就是为此留的）；但与其搞「单文件例外」  
这种容易说错的安排，不如整个仓库统一按 LGPL 走。  
**逐个上游文件、它们的版权声明、以及生成器与产出的对应关系见 [NOTICE](NOTICE)。**  
（重新生成表需要自备 FFmpeg 源码 —— 生成器的默认路径是作者的本地路径，见上面的「目录」。）

**代价**：GPL 侧的编码器（x264/x265）链不了，编码只能走宽松许可的实现或硬件  
（Android MediaCodec）；引第三方 crate 也只挑宽松许可的（Apache-2.0 / MIT / BSD）。  
LGPL 作为**库**被 MIT 的应用依赖是没问题的；反过来（把 LGPL 代码并进 MIT 的库再改许可）不行
