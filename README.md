# v2videos

用 **Rust** 研究「视频之间的编码格式转换」—— 也就是把一种视频（**容器 + 视频编码 + 音频编码**）  
转成另一种，整条链路的每一段都拿出来看看：在纯 Rust 里能做到什么、边界在哪、代价是什么。

> 名字里的 `v2v` = **v**ideo **to** **v**ideo。

## 转换链路

一次转换拆成四段，研究也按这四段走：

```text
         ┌─ 解封装 ──► 解码 ──► 像素域 / 采样域 ──► 编码 ──► 封装 ─┐
输入 ────┤   demux      decode     (YUV / PCM)        encode   mux   ├──── 输出
         └──────────────────────────────────────────────────────────┘
```

中间那层「像素域 / 采样域」是关键的解耦点：两端互相不认识，只认中间那份裸数据。

## 目录

> `mp4v` / `aac` / `mpeg12`）是 **LGPL** 侧 —— `ls crates/` 就能看出边界。

```text
  vc1               VC-1（**WMV3**）解码：Simple/Main profile、渐进、I/P —— 序列头 → 帧头 → 位平面 →

  v2v-ogg           Ogg 解封装：页（含跨页续接的包）/ 流识别 / 逐包时间戳。

                    容器不依赖任何编解码器；页层自带 256 KiB 读缓冲

                    **只有解码器**，且不做 floor 0（LSP）—— setup 阶段明确报 `Unsupported`。
                    全部概率模型都逐流携带，所以它是 MIT 侧、没有派生码表
  mpeg12            MPEG-1/2 **解码**（本 crate 自身零 unsafe，**且依赖闭包里也没有 unsafe**

                    MPEG-2 的 progressive 帧图、隔行帧图的场 DCT / 场运动、4:2:2 / 4:4:4 色度
  v2v-mpeg12-simd   同一个解码内核的 **unsafe / FFI 变体**：可单独编 `.so` / `.a` 给宿主链；

  v2v-filter        像素域算子：缩放（bilinear / bicubic，**缩小时核按 `src/dst` 拉伸抗混叠**）、
```

## FFI：哪些 crate 碰了它，性能账怎么算

FFI 有两个方向：

- **进站（我们调 C）**：`crates/v2v-android` 调用平台媒体框架，`crates/v2v-audio-ffi` 调用可选的原生音频库。
- **出站（C 调我们）**：`crates/v2v-capi`。

其余全部纯 Rust（`msmpeg4` / `mp4v` 的 NEON 走 `std::arch` intrinsics，不跨语言
边界，**不算 FFI**）。

| | 边界在哪 | 为什么需要 |
| --- | --- | --- |
| `v2v-android` | C：`c/media_encoder.c`（NDK 的全部句柄/生命周期/错误收在这一个文件）<br>Rust：`src/ffi.rs`（唯一的 `extern` 声明 + 调用边界） | Android 的**硬件** H.264 编码器只能走 NDK（`AMediaCodec` / `AMediaMuxer`）—— 纯 Rust 侧链不了厂商的编解码 HAL |

它的 API（`Mp4HwWriter`）是安全的：裸指针不外漏、`Drop` 兜底、`!Send`
（MediaCodec 不是线程安全的）。非 Android 平台编译同名桩，运行时明确报 `Unsupported`。

### MP3 解码

CLI 默认使用纯 Rust 解码，用 `--mp4` 将 AVI / ASF 中的 MP3 音轨转为 AAC，或者加
`--pcm` 写未压缩音频。C 调用方可用 `v2v_adec_open` 的 `format_tag = 0x0055`，
采用 `feed` / `next` 读逐声道 PCM。Rust 的 `Framer` 接收连续的 MPEG 帧字节，
允许拆包和合包。首版从流起点顺序解码，输出包含编码器延迟的原始 PCM。裸 `.mp3` 文件的标签、
无缝裁剪、seek、free format 及纯 Rust 的 8 kHz mixed block 暂未覆盖。

安装带开发文件的 libmpg123 与 pkg-config 后，可以选择 FFI 后端：

```bash
cargo run -p v2v-cli --features mp3-ffi -j 2 -- convert --mp4 -o out/ input.avi
crates/v2v-capi/build-products.sh --formats "avi,mp3-ffi" --name avi_mp3_ffi
```

C ABI 单独开 `mp3` 使用纯 Rust。两项都开时优先 mpg123。交叉编译设置
`V2V_MPG123_LIB_DIR` 指向目标平台的原生动态库目录。

`v2v bench --cases decode/mp3 sample.avi` 在解封装后计时，启用 CLI 的
`mp3-ffi` feature 时会分别报告两个后端。

#### MP3 纯 Rust 解码提速（2026-11-24）

Apple M3、release、单线程。`v2v bench` 对同批完整帧流热跑 7 次，取最快一次。
短素材重复为更长的 AVI 音轨来测吞吐，质量单独对未经重复的输入对账。

| 语料 | 采样率 / 声道 | 原版 ms | 优化后 ms | 提速 |
|---|---|---:|---:|---:|
| 真实音乐 | 44.1 kHz / 2 ch | 461.84 | 269.64 | 1.71× |
| 真实音轨 | 48 kHz / 2 ch | 615.13 | 351.87 | 1.75× |
| 合成攻击包络 | 22.05 kHz / 1 ch | 249.06 | 130.33 | 1.91× |
| 固定种子噪声 | 8 kHz / 1 ch | 168.82 | 106.32 | 1.59× |

合计 4,730,112 个 s16 样本值在纯 Rust 优化前后逐样本一致。四段 AVI 转 MP4 PCM
与 FFmpeg 的最大差为 1–2 LSB。

纯 Rust、mpg123 与 FFmpeg 的最新三路实测见[单线程速度矩阵](#10-单线程速度矩阵)。

### C ABI：`libv2v_capi`

`crates/v2v-capi` 是**全仓唯一的出站 C 表面**。一个 `.so`、一个 `v2v_abi_version()`、
一个 `v2v_last_error()`（每线程）、一张派发表（`codec_id → 构造器` 只在那里 `match`）。
头文件 `crates/v2v-capi/include/v2v.h` 只用 C11 标准头，**不需要 Rust 工具链就能编过**。

| 层 | 符号 | 覆盖 |
| --- | --- | --- |
| 公共 | `v2v_abi_version` / `v2v_last_error` / `v2v_last_error_kind` | 版本、错误通道 |
| 容器 | `v2v_probe` / `v2v_demux_*` | ASF、AVI、MP4 |
| 解码 | `v2v_vdec_*` / `v2v_adec_*` | VC-1、MS-MPEG-4 家族、MPEG-4 Part 2、WMA、MP3 |
| 编码 | `v2v_venc_*` / `v2v_aenc_*` | MP43、MPEG-4 Part 2、AAC |
| 封装 | `v2v_mux_*` | ASF、MP4 |
| 播放 | `v2v_player_*` | 解封装 + 解码，逐帧 / 逐样本，`seek(ms)` |
| MPEG-1/2 | `v2v_mpeg_*` / `v2v_ps_*` | `mpeg12` feature，默认关 |
| 硬件转码 | `v2v_transcode` / `v2v_hw_supported` / `v2v_wma_to_wav` | `hw` feature，默认关 |

四条约定（头文件里也写了一遍）：**panic 不穿透**（每个入口 `catch_unwind`）、
**谁分配谁释放**（借用指针都注明活到哪次调用）、**出参首字段是 `size`**（库按
`min` 写，于是加字段不破坏 ABI）、**句柄只能在一个线程用**。

帧和样本的指针都是**借用**的（省一次 720p 拷贝 ≈1.4 MB/帧）。想存起来就用
`v2v_planes_copy_to`：拷进你自己的缓冲，可以带 padding，不用自己按 stride 逐行搬 ——
「色度是 `ceil(width/2)` 宽、`ceil(height/2)` 高」这种细节写错**只会花屏，不会报错**。

产物：`crates/v2v-capi/build-products.sh` 默认出 `min`（默认 feature）与 `full`（加
`hw` / `mpeg12`）。**按格式裁剪**用 `--formats`：

```bash
crates/v2v-capi/build-products.sh --formats "asf,wmv3,wma" --name decode_only
```

它走 `--no-default-features`，没开的容器 / 编解码器**连码表都不编进去**（`v2v-tables`
的 feature 跟着缩），符号集也只剩开的那几族 —— 没开的那族 `dlsym` 会拿到 NULL。
MP3 接入前的快照（macOS / release）：`min` 1.2 MB、`full` 1.5 MB，只开 `asf,wmv3,wma` 的产物 **688 KB**。
同主版本就同 ABI —— 区别只是「有没有」，不是「布局不一样」。

（**别把符号个数写进文档**：加一个函数它就变，而它是「数出来的」不是契约。
要知道当下几个，`nm -gU dist/libv2v_capi_min.so | grep -c ' _v2v_'`。）

验收不靠「自己的 Rust 测试调自己」：`crates/v2v-capi/tests/smoke.c` 是个纯 C 程序，
`dlopen` 打开产物、按头文件的声明取函数指针类型，走
`probe → open → info → 读帧 → seek → demux`。头文件写错它编不过，符号不在 `.so` 里
它 `dlsym` 不到 —— 这两件事 Rust 侧测不出来。

### 性能（真实样本：`testing/sample.wmv`，1280×720@30，4138 帧 / 138.4 s）

**基线：全软件栈（无 FFI），2026-10-20 在开发机实测：**

| 环节 | 我们（纯 Rust） | `ffmpeg` | 差距 |
| --- | --- | --- | --- |
| VC-1 解码（写 /dev/null） | **11.4 s**（363 fps，12.1× 实时） | 11.4 s（363 fps） | **持平** |
| WMV→MP4 转码全栈（4 Mbps + AAC 128k） | **42.9 s**（96 fps） | 11.7 s（352 fps） | **3.7×（按 CPU 时间 2.1×）** |
| 转码质量 SSIM / PSNR（对 VC-1 解码参考） | 0.9621 / **38.83 dB** | 0.9713 / **40.77 dB** | −1.9 dB |
| 解码产物 | **与 `ffmpeg` 逐字节一致**（5.7 GB md5 相同） | — | 0 |

⚠️ 上面这组数字**必须在空载机器上量**（2026-10-20 早上量出「解码 1.73× / 转码 6.7×」，
当时机器负载 13，全被污染 —— 同机空载复测就是上表的数。单次测量不是事实，见 AGENTS.md）。

⚠️ **「持平」只对这份 720p 样本成立**：换成 1920×1080 那份（3719 帧），单线程是 **1.80×**
（`crates/vc1/tests/decode_bench.rs`，口径见下面 §1）。两份样本不要混着引用。

📏 **这些数字现在有机器可读的基线了**：`v2v bench --baseline-dir bench/baseline <样本>`
打 TSV（`case` / `n` / `total_ms` / `per_unit` / `unit` / `ref_per_unit`），
`--check` 对着基线卡回归 —— **只卡「我们 / ffmpeg」的比值**，绝对毫秒只提醒
（CI runner 上绝对量能差 2×，比值才是稳定的）。下面这些手工表仍然是「某一版代码在某台
机器上」的快照，**别拿它当门**；口径与限制见 `bench/README.md`。

**FFI 硬件路径（同一个样本、同码率 4 Mbps，2026-10-20 实测）—— 两个差距都解决了：**

| | 软件栈（无 FFI） | ffmpeg | **FFI 硬件（本机 VideoToolbox H.264）** |
| --- | --- | --- | --- |
| 全链路转码 | 42.9 s（96 fps） | 11.7 s（352 fps） | **7.1 s（583 fps，19.5× 实时）—— 反超 ffmpeg** |
| SSIM（对 VC-1 解码参考） | 0.9621 | 0.9713 | **0.9820 —— 全场最高** |
| PSNR（同上） | 38.83 dB | 40.77 dB | **42.45 dB（+3.6 / +1.7 dB）** |
| 体积 | 71.34 MB | 71.05 MB | **71.04 MB** |
| 音频时间轴 | **偏移 0** | 1024 帧 priming | **偏移 0**（音频走我们的 AAC） |

读法：解码两侧逐字节一致（上表），所以质量与速度的差距全在**编码器** —— FFI 路径
把编码换成**硬件 H.264**：专用电路（CPU 释放给播放本身）+ 高一代的标准，
实测同时吃掉「速度差」（96 → 583 fps）与「质量差」（38.8 → 42.5 dB，反超 ffmpeg）。
macOS 走 VideoToolbox、Android 走 MediaCodec（结构相同，真机数字待设备接入后回填）。

速度从 33.7 s 到 7.1 s 的三步（都在 perf/decode，输出逐位不变）：
① MC 插值 NEON 化（解码 11.4 → 10.0 s）；
② 分段剖析定位瓶颈（VT 硬件编码只占 0.9 s，AAC 5.8 s，解码 10 s）；
③ **GOP 并行解码 + 有序提交 + 音频独立线程**——并行解码的关键是**提交顺序 = 帧间
   参考顺序**，乱序提交让 P 帧参考错帧（产物 71 → 239 MB），故 worker 只解码、
   帧进按序的 ready 表，主线程按 seq 提交；内存用滑动窗口（seq < next_submit + 32）
   兜住，不用 in_flight 计数（主线程一减就下溢 → 双向死等）。

复现（全片 ≈34 s）：

```bash
cargo run --release -p v2v-android --example wmv_to_mp4_hw -- \
```

**两条输出路**（`v2v convert`，默认 `.wmv`）：

```bash
# .wmv：视频重编码成 MP43，音频**直通**（零损失），会做 PSNR 校验
v2v convert in.wmv -o out/

# .mp4：视频重编码成 MPEG-4 Part 2（-g 给 GOP，默认 250 帧 ≈ 10 秒；0 = 全 I 帧），
#       音频 WMA / MP3 / Vorbis → PCM → **AAC-LC**（--pcm 可退回未压缩 PCM）
v2v convert --mp4 -g 12 in.wmv -o out/

# .mp4 输入（H.264 硬解 + AAC 直通）→ 再出 .mp4
v2v convert --mp4 in.mp4 -o out/

# 纯音频输入（.ogg）：没有视频轨，照样出 .mp4 —— moov 里只有一条 soun 轨
v2v convert --mp4 in.ogg -o out/          # AAC-LC（默认）
v2v convert --mp4 --pcm in.ogg -o out/    # 未压缩 PCM，逐字节可验

# 只抽音频成 .wav（PCM16）：不解视频、不重编码。**不看视频轨**
v2v convert --wav in.ogg -o out/

# 无损剪切 / 拼接：只搬样本，不解码、不重编码（只能切在关键帧上）
v2v trim --start 10 --end 15 -o cut.wmv in.wmv
v2v concat -o ab.wmv a.wmv b.wmv

# 扫描：递归找「我们能转的」，只读头部（一个样本都不读）
v2v scan /path/to/game/data
v2v scan --tsv --all . | awk -F'\t' '$11 ~ /mp4/ {print $1}'
```

**输入按魔数认容器**（ASF / AVI / MP4 / Ogg 的字节特征），**不看扩展名** —— 扩展名会骗人
（游戏资源里 `.wmv` 其实是 MP4、`.bin` 其实是 ASF 的情况都见过）。`--mp4` 说的是
**输出**格式，所以 `v2v convert --mp4 in.mp4` 是「`.mp4` 进、`.mp4` 出」。`.mp4` 输入
的视频走 **VT 硬件解码**（macOS；别处明确报不支持），音频若是 AAC 且输出也是 AAC
就**原样搬帧**、不解码。

**为什么 `.mp4` 必须重编码**：MP4 / 3GP 容器**不收 MP43**（`mp4`/`3gp`/`3g2` 三个 muxer 都报  
`codec not currently supported in container`），`mov` 收但是单向街 —— 写出来的东西 ffmpeg  
自己读不回来。WMA 同理。所以 `.wmv → .mp4` 这条路上视频必须过一遍 MPEG-4 Part 2 编码器，  
音频必须解成 PCM 再重编码（默认 AAC，`--pcm` 则是原封不动的 `sowt`）。

**还没做（解码侧）**：VC-1 的 **B 帧 / 隔行 / Advanced profile**、overlap smoothing、
多分辨率、`rangered`、重同步标记（见下一段）。**MP41** 的 MB 层分支写好了，但 ffmpeg
只有 `msmpeg4v2` / `msmpeg4v3` 两个编码器 —— **造不出 v1 的流**，也就拿不到对账样本，
所以输入被明确拒绝。（MP42 已经对上了，见能力矩阵。）

**H.264 只有硬件解码这条路**：macOS 上是 VideoToolbox，别处没有。纯 Rust 的 H.264
解码器**没有计划** —— 它不是「再写一个模块」，而是一整套 CABAC / 去块滤波 / 帧内预测
的整数管线，投入与收益不成比例。所以 `.mp4` 输入在非 macOS 上是明确报不支持，而不是
悄悄降级。另外 `avc1` 的 **High 10 / 4:2:2 / MVC** 也没验过（VT 支持与否取决于机器）。

**VC-1 走到哪一步**：`v2v-vc1` 已经**整条链路通了** —— 序列头（容器 extradata 里的
`STRUCT_C`）、帧头（I/P）、帧头里的**位平面**（逐宏块跳过标志那类整帧位图，7 种编码 +
差分算子）、**宏块层**（I/P 的 MB 语法、DC/AC 预测、系数解码、四种变换落像素）、
**运动补偿**（四分之一 / 半像素插值、色度双线性、边缘复制、亮度补偿）、**环路滤波**
（含上游那套「落后两行两列」的调用时序），最后出 YUV420P。

判据是外部的、两条：**位游标**（I 帧宏块层解完落在帧尾，实测差 0～7 位）把「语法解对」
与「像素重建对不对」分开；**逐帧逐像素**（`ffmpeg` 吐裸帧边解边比）要求 **0 差**。
范围限定在 **Main profile / 渐进 / I/P**：Advanced profile、B 帧、隔行、
`res_fasttx=0`、overlap smoothing 遇到就明确报错。**已经接进 CLI**（`v2v convert` 认 `WMV3`，
GOP 并行解码也开着；「解码顺序 ≠ 显示顺序」按 PTS 出帧处理）。

**还没做（编码侧）**：MPEG-4 Part 2 的 **B 帧**与 8×8 运动补偿、AAC 的 **PNS** 与**逐带** M/S
掩码（现在只做逐帧 —— 全部带一起选；TNS 只覆盖长窗）、WMA **编码器**（现在只能解）、
MP4 的**分片**（`moof`）与**编辑列表**（`edts`/`elst`）、其他容器与编解码器。

**还没做（解码侧）**：AAC 的 **PNS**、**强度立体声**、`pulse_data`、`gain_control`、SBR / PS ——
都**明确报 `Unsupported`**，不静默跳过。PNS 与 IS 规范不要求 bit-exact，所以也不进
「对 `ffmpeg` ±1 LSB」那条判据（测 ffmpeg 位流时用 `-aac_pns 0 -aac_is 0` 关掉）。

## 与 FFmpeg 的性能和质量对比

> 视频质量对比。2026-11-24 的 [AAC 实测](#4-aac-lc-编码性能与质量2026-11-24)、
> [MP3 实测](#mp3-解码)、[MPEG-4 Part 2](#8-mpeg-4-part-2-编码提速2026-11-24)与
> [MP43 提速](#9-mp43-量化提速2026-11-24)见对应章节。

**口径**（这几条不一起看就会读出错误结论）：

- 真样本、**同一台机器、背靠背 A/B**；机器空闲时量（有负载时绝对值明显变慢，所以只看比值）
- `ffmpeg 9.0.1`（本机），`-threads 1`；**下表（§2）是我们的视频编码还是单线程时量的** ——
  `--threads` 当时只作用于 AAC 声道并行。**现在 `--threads > 1` 会把视频也按 GOP 并行**（见 §2.1）
- 「倍数」= 我们 ÷ ffmpeg，**大于 1 = 我们慢**
- ⚠️ **同一个 `-qscale` ≠ 同一个码率**：两边的量化器实现不同，同 q 下体积差 ±20% —— 每行都带体积
- ⚠️ **PSNR 是自己解码后逐帧算的**：`ffmpeg -lavfi psnr` 在**跨容器**（源 `.wmv` 对产物 `.mp4`）
  或时间戳不齐的两个输入上会**错位配对** —— 同一份产物它能给出**恒定 24 dB** 的假数，
  而且**换 qscale 数字几乎不动**（那正是错位的指纹：真质量随 q 变，错位比较不随）。
  归零 PTS、`-fps_mode passthrough` 都救不回来。**可信的算法是把两边都 dump 成原始 YUV 逐字节比**
  （逐帧 MSE → PSNR）—— 见文末「踩过的坑」

| 真样本 A | MP43 | 320×240 | 5201 | 0.12 | 0.07 | **1.92×** |
| 真样本 C | MP43 | 160×120 | 153 | 0.03 | 0.20 | **1.49×** |
| 真样本 E | WMV1 | 360×240 | 1379 | 0.08 | 0.06 | **1.91×** |
| 真样本 D | WMV1 | 512×512 | 249 | 0.12 | 0.15 | **2.80×** |
| 真样本 F | WMV2 | 176×144 | 767 | 0.07 | 0.10 | **1.06×** |
| 真样本 G | WMV2 | 320×240 | 898 | 0.14 | 0.16 | **1.11×** |
| 真样本 H | WMV2 | 640×360 | 9541 | 0.36 | 0.35 | **1.03×** |
| 真样本 I | WMV2 | 1280×720 | 600 | 2.35 | 2.48 | **0.98×** |
| 真样本 J | WMV2 | 1280×720 | 600 | 1.45 | 1.37 | **1.13×** |

⚠️ ffmpeg 每跑一次要付**进程启动**（20–30 ms），帧少的样本里它占大半 —— 所以上表是
「两边都减掉解 1 帧那一趟」的**纯解码吞吐**（`(我们 N − 我们 1) / (ffmpeg N − ffmpeg 1)`）。
不减的话，153 帧那行会算出「我们快 4 倍」这种纯属分母灌水的数。
⚠️ **720p 那两行只比了前 600 帧**（不是口径变了，是**内存**：对账测试把两边的帧都摊在内存里，
720p 整段约 11 GB，实测把 swap 打满 —— 见 `TODO.md`）。帧数少了靠「去启动」那一步兜住。
**解码正确性**：三档编码的真样本都是**逐像素最大差 0**（见上面「状态」那节）。
（这张表比提速前**快了 1.75–2.67×**：位读取器从逐位读改成字宽、VLC 加 9 位快表、
列变换 4 通道一批（读的时候不再拷块）、RL 符号编进快表、几处内层写法 ——
**WMV2 那三行已经追平 ffmpeg**（1.03–1.11×），MP43 还慢 1.5–1.9 倍。
再往下要动 IDCT 的 SIMD intrinsics —— 那要新写 `unsafe` 内核（本仓唯一放开 `unsafe` 的地方
是 `kernel::simd`，目前只放了**编码器**的 SAD），见 `TODO.md`。）

**VC-1 那一档**（`crates/vc1/tests/decode_bench.rs`，口径同上：只解视频、单线程、
两边都减掉「解 1 帧」那一趟）：

| 样本 | 编码 | 尺寸 | 帧数 | 我们 ms/帧 | ffmpeg ms/帧 | 倍数 |
|---|---|---|---|---|---|---|
| 真样本 K | VC-1 Main | 1920×1080 | 3719 | 10.83 | 6.03 | **1.80×** |

第一版（一行没优化）是 **4.35×**，现在 **1.80×** —— 按倍数算**快 2.4 倍**，逐帧逐像素仍然 0 差。

⚠️ **只信倍数，别信绝对毫秒。** 这张表的 `ms/帧` 会被**机器状态**整体抬放：同一份代码，
在「另一个会话占着核」的时候量出 20.78，空下来再量是 10.83 —— 而 **ffmpeg 那一列同样从
10.46 掉到 6.03**。绝对值变了一半，倍数只从 1.99 动到 1.80。所以跨会话比绝对毫秒必然被骗，
**同一会话背靠背的 A/B 才算数**（下面每一条都是这么量的）。

做过的事，按收益从大到小：

- **去掉「每块克隆一次帧头」**：`PFrameHeader` 里带着两张位平面（各一个 `Vec<u8>`），
  而 `decode_p_block` / `pred_mv` / `mc_*` 都是**每个块**进一次 —— 一次克隆 = 一次 malloc
  + 几 KB memcpy。只取标量、位平面在短作用域里借一下就够了。**这一刀最大**。
- **`mspel_mc` 改成常量泛型 `mspel_mc::<W>`**：中间结果缓冲正好 `(W+3)*W`，不再为 8×8
  的块白开 16×16 的再清零一大半；每个 `W` 各自单态化，内层循环完全展开。**约 9%**。
- `[profile.release] codegen-units = 1`（约 9%）
- **MV 恰好是 `(0,0)` 且无亮度补偿时直接搬参考块**（约 4%）：跳过的宏块在静态素材里很常见，
  通用路径要 `load_ref`（逐像素 clamp）+ 每个像素一次插值
- `load_ref` 加「整块在画面内」的快路：逐行 `copy_from_slice`，不做逐像素 `clamp`
- `hpel_mc` 把 `(hm, vm)` 四条路提到循环外；`mspel_mc` 两趟都把行偏移与系数选择提出来
- MC 的本地缓冲 32×32 → 24×24、`put_block` 改成按值收块（省掉每块一次 128 字节拷贝）

⚠️ **试过但没用的**：给这几个内核手写 NEON intrinsics 只快 **1.3%**（原因：热点是**串行位解析**，
能向量化的 MC 只占 ~21%，而内核是按**行**调的、一行 16 像素就是一条 NEON 指令，
调用开销把向量宽度吃干净了；何况 `sad_row16` 那边 LLVM 本来就生成 `uabd.16b` + `udot.4s`）。
结论与教训记在本地 `TODO.md`，分支已删 —— **解码器**上那个 `unsafe` 不值得为它破例
（后来只给**编码器**的 SAD 破了一次，就是 `kernel::simd` 那一份：它每个候选是一整块
16×16、调用开销摊得开，实测收益是真的）。

**剩下的 1.80× 是什么**：ffmpeg 的 MC / IDCT / 环路滤波是手写汇编核，本仓解码侧纯标量、
零 `unsafe`（全仓唯一那处 `unsafe` 在 `kernel::simd`，服务编码器的运动估计）；
再加上它的解码器按片并行、我们是单线程。再往上要动架构（编译期行宽、帧级流水），
不是「再抠几个循环」能到的。

读法：

- **`.wmv` 路的「不可比」不是我们挑的**：`msmpeg4v3` 编码器**拒绝重复时间戳**，ffmpeg 只能把
  **变帧率（VFR）的源转成恒定帧率** —— 补帧、重写时间轴，帧数甚至从 1379 变 1568。
  帧都对不上，逐帧比 PSNR 就没有意义（拿它硬比会得到 11–17 dB 这种假数）。
  **我们保留源的时间轴**（帧数与时间戳都不动），所以只有 CFR 源（真样本 A）两边能直接比。
  这本身是**我们比 ffmpeg 强的一点**：这条路上它改写了时间轴，我们没改。
- ⚠️ **`.wmv` 那几行有个 ±2% 的噪声底，而且来自 ffmpeg 那边**：它的 `msmpeg4v3` **输出不确定** ——
  同一份输入、同一串参数，三次跑出**三个不同的 MD5**、体积差 ±2%（实测只在部分素材上发作：
  一份抖 1.5%、另一份抖 1.8%，三份完全稳定）。**我们自己两次跑是逐字节相同的。**
  所以 `.wmv` 行的「体积比 / PSNR ffmpeg」是 **3 次取中位**；比值本身在负载下还会再飘 ±15%（只当量级看）。
- **瓶颈是编码，不是解码**：解码慢 1.0–2.8×（§1），编码慢 **9–14×**（`.wmv`）与 **3.6–15.8×**（`.mp4`）。
  （提速见 `TODO.md`，这一轮五笔：运动搜索**粗搜改菱形/区域搜索**、细化层改**八邻域步进**、
  候选**一生成就夹进可编码范围**（顺手修掉一个潜伏的编解码分叉）、正向 DCT 换 **LL&M 蝶形**、
  `pad_planes` 与每宏块拷贝改逐行 memcpy（最后一笔**输出逐字节不变**）。
  **合计 `.wmv` 编码快约 30~35%、`.mp4` 快 13~14%，五笔的质量要么持平或更好、要么逐字节不变。**
  ⚠️ 表里的数字是**合并 `feat/aac-psy` 之后**重测的一整套 —— 那一版把 `.mp4` 的量化换成
  **MPEG 型（`quant_type = 1`，规范默认 CSF 矩阵）**，代价是编码本身慢约 **8%**，换来的是同体积下更好的感知质量。）
- **真样本 K 那行要分开读**（1080p、VC-1 源，q=6、`-g 12`）：**解码只慢 1.78×**（§1 已优化），
  **编码慢 ~4.9×**（我们 25.3 ms/帧、ffmpeg 5.1）—— 差距全在编码。**等体积下 ffmpeg 约高 1.2 dB**：
  它 q=5 是 26.1 MB / 42.49 dB、q=4 是 30.8 MB / 43.79 dB，插到我们 29.1 MB 那个体积上是 ~43.3 dB
  （我们 42.1）。这条样本比上面那几行（320×240～720×720 的 WMV1/2 源）差距大，两种可能都该记着：
  这份素材**运动量大得多**（1080p 摇镜头，P 帧残差大），而我们的运动估计是纯标量；
  另外它的 P 帧成本里还有**每帧一次 1080p 的亮度补偿查表**那类本仓独有的代价。
  同 qscale 下多花的 26% 位买回了 +0.74 dB，但**等体积还是落后** —— mp4v 编码器的运动估计
  与 DCT 没有任何 SIMD，是这轮对表里**唯一没被优化的那一环**。
  还有两个口径要交代：① ffmpeg 在这条样本上插了 **67 个 I 帧**、我们只有 **50 个**（固定间隔，
  无场景切换检测）—— 它多花的 I 帧买回了健壮性，我们买的是 P 帧质量；② 本行是**单线程**口径
  （我们 `--threads 1` 35.7 ms/帧），`--threads 8` 是 **10.8 ms/帧**（解码池 + 编码池两级流水）。
- **`.mp4` 路现在是「同体积打平 + SSIM 更高」**：六条能比的行里 PSNR 全在 **±0.1 dB** 内
  （体积 0.96–1.06×），而**感知指标更高** —— 见 §6 的按分辨率扫描（同一批样本上 SSIM 7/7 档都赢）。
  这跟合并前不一样（那时是「PSNR 高 0.9~1.6 dB 但体积大 1.06~1.38×」）：换成 MPEG 型量化之后
  两边的**量化器家族一致了**，所以同体积下 PSNR 拉平、把差别让给了 SSIM。
- **`.wmv`（MP43）路反过来**：720p 上 PSNR **更低**（−1.09 / −0.53 dB）—— 只是它同时更小（0.80–0.87×）。
  补一个 q 扫描（400 帧）看趋势：**同 q 下 ffmpeg 每一档都更好**，
  且**码率越高差距越大**（真样本 I：q=2 −4.01 dB、q=3 −1.41、q=4 −0.53；
  真样本 J：−2.33 / −0.52 / −0.32）—— 我们的 MP43 编码器**高码率那一段质量明显弱**，
  体积优势也换不回来。这是下一步编码器该看的地方（`TODO.md`）。
- **这一轮之后我们这边更快了**：按上面的调研做了两笔**输出逐字节不变**的改动
  （SAD 重塑 + AC 量化改倒数乘法），背靠背 A/B 实测 720p `.mp4` **−10.6%**、`.wmv` −3.2%。
  所以上表「我们 ms/帧」那列是优化**前**量的，偏保守；**倍数**那列基本不动
  （`TODO.md` 有完整记录与复核口径）。
- **720p 上端到端更慢**：`.mp4` 路 13.8–17.7×（小样本上是 2.0–6.5×）——
  我们的 mp4v 是纯标量，代价随像素线性涨，而 ffmpeg 那条路吃 SIMD；`.wmv` 路 14.3–14.8×（与小样本的 11.8–13.6× 同档）。

### 2.1 视频并行之后（2026-10-17 实测）

`--threads N` 现在把**视频编码也按 GOP 并行**：主线程解封装 + 解码（参考链天然串行，
留在生产者那一条），每个 GOP 派给 worker 池；`.wmv` 那条**主线程喂完最后一个 GOP 也下场一起编**
（worker 数 = `threads − 1`，免得 8 核上多出一条白抢核的线程）。

**VC-1 输入时解码也并行了**（`crates/vc1/tests/gop_start.rs` 钉着前提）：**每条 GOP 用一条
全新的解码器、从它的 I 帧独立解**，像素与整条链逐帧 0 差（真样本 278 个关键帧全查过）。
所以 `--threads > 1` 时是**两级流水**：解码池（`threads/4` 个核）→ 编码池（剩下的核）。
比例按实测的「解码 : 编码 ≈ 1 : 1.9」分 —— 给解码多了反而把编码饿死。
⚠️ 只在 `gop_len > 1` 时开（`-g 0` 每帧一个 GOP，起解码器的开销比解这一帧还大）。
**产物与串行逐字节相同**（300 帧实测 md5 一致）。

**`--threads 1` 逐字节不变**（老路一条没动）。`--threads > 1` 的产物与串行**逐字节相同** ——
MP43 编码器没有跨 GOP 状态，所以每个 worker 起新编码器编出来的字节完全一样；
`.wmv` 的包排布也一样（结果按 GOP 序号归位后与音频按 pts 合并，正好等于串行读到的顺序）。
这条不变量有测试钉着（`crates/v2v-cli/tests/convert.rs::parallel_gop_encoding_is_byte_identical`，
合成源、无样本、CI 里真跑）。

一段 720p（1280×720）真样本的**前 300 帧**，`-q 3`，两边同 qscale、同帧数上限：

| 路 | 设置 | 我们 | ffmpeg | 倍数 |
|---|---|---|---|---|
| `.mp4` 全 I 帧（**我们的默认** `-g 0`）+ AAC | `--threads 10` | **0.85 s** | 0.49 s | **1.73×** |
| `.mp4` P 帧 `-g 12`，只视频 | `--threads 10` | **0.83 s**（串行 3.40） | 0.47 s | **1.77×** |
| `.wmv` `-g 12`（**ffmpeg 的默认**），只视频 | `--threads 10` | **1.31 s** | 0.81 s | **1.62×** |
| `.wmv` `-g 250`（**我们的默认**），只视频 | `--threads 10` | 5.90 s | 0.82 s | 7.20× |

（同一批参数重复测会在 ±5% 内飘，看量级别看末位。）

⚠️ **量法**：三次取中位、**丢掉第一次** —— 刚构建完（或系统刚忙过）的第一跑能偏 15~20%，
本表第一版就因此把 `.mp4` 那条算成了 3.2×。同批次背靠背测出来的比值才可信。

读法：

- **并行度上限就是 GOP 数**。`-g 12` 时 300 帧 = 25 个 GOP，10 线程吃得下；
  `-g 250` 时只有 **2 个** GOP —— 再多线程也没用。这是格式约束（P 帧只参考前一帧的
  **重建**帧，链是串的），不是实现问题。**要快就 `-g 12` 上下**，别拿 `-g 250` 配 `--threads 8`。
- **`.mp4` 的 P 帧那条**（1.77×）：mp4v 的运动估计每个宏块要评
  **150~200 个候选**（三个起点各走一遍菱形 + 每处补一圈 ±2 全搜 + 半像素细化），
  而 ffmpeg 的 EPZS 只评二十来个 —— 单这一项就比它**整个宏块**还贵。
  换来的是同 qscale 下体积只小 **0.4%**（9.10 vs 9.14 MB，PSNR 49.60 vs 49.76 dB）：
  **投入产出极不对称**。已经做了四笔（见下）：**基于 SAD 的帧内预判**、**去掉 ±2 收尾**、
  **粗搜菱形 8 点改 4 点**（这笔白赚：−14.7% 速度、体积 +0.02%、PSNR 不变）、
  **帧内预判倍数收到 1** —— 把这一档从 2.78× 一路收到 **1.77×**。
- 同 qscale 的质量（300 帧、逐字节比原始 YUV 算的）：`.mp4` 我们 49.60 dB / 9.10 MB、
  ffmpeg 49.76 dB / 9.14 MB；`.wmv` 我们 49.74 dB / 9.67 MB、ffmpeg 50.37 dB / 8.76 MB。
  **`.mp4` 两边基本打平，`.wmv` 它略好且更小。**
- 串行→并行的加速比：`.mp4`（P 帧）**4.3×**（5.54 → 1.28）、`.wmv` 约 4.8×。
  ⚠️ 上不去 8× 的**实测原因**：并行跑的总 CPU 比串行高 **49%**（8.8 s vs 5.9 s）——
  跨核搬帧（解码在一个核、编码在另一个核）的缓存代价，不是负载不均。
  上不去 8× 的原因：解码那 0.37 s 在关键路径上是串的、25 个 GOP 摊到 10 个 worker
  有长尾、以及 AAC 编码（约 0.9 s CPU）要占掉一个核。

#### 帧内试编的 SAD 预判（`.mp4` 的 P 帧）

P 帧的每个宏块原本要把**帧间与帧内各真编一遍**（6 次 DCT + 量化 + **两遍**熵编码）再比位数 ——
这是每宏块最贵的一段。现在先用一个便宜代理判一下：

- 帧内编的是**原始块**（MPEG-4 帧内没有方向预测），代价与「块减去自身均值之后的能量」强相关；
- 帧间的代价与残差 SAD 强相关 —— 两者都是同一量纲的绝对差之和，可以直接比；
- **帧间最优 SAD × 2 仍小于帧内块的 AC 能量**时，跳过帧内那一趟（约 512 次加减，换掉约 3000+ 条指令）。

720p 前 300 帧实测（两个真样本，同一批参数、三次取中位）：

| 样本 | 串行 | 并行 10 | 体积 | PSNR |
|---|---|---|---|---|
| 运动较多的那份 | 5.54 → **4.81 s**（−13%） | 1.28 → **1.12 s** | +0.015% | 49.60 → 49.59 dB |
| 几乎静止的那份 | — | 0.72 s（基本没变） | +0.09% | 54.49 → 54.49 dB |

**收益与内容相关**：静止素材上宏块本来大多走 skip，帧内那一趟早就跳过了，预判自然没得省。
倍数 `INTRA_SKIP_RATIO = 2` 是量出来的（1 更激进：再快 3%，但体积 +0.42%；3 更保守：体积 +0.007%，但慢 4%）。

⚠️ 这笔**会改变产物**（决策不再逐位精确）—— 所以质量必须对着真样本 + 原始 YUV 逐字节验，
不能只看「没报错」。上面那两个样本是这么验的。

### 5. 这套量法踩过的坑（写下来免得重踩）

1. **`ffmpeg -lavfi psnr` 会在时间戳不齐时错位**：同一份产物，它给 24 dB、自己解码逐帧算是 49 dB。
   症状是「**PSNR 不随 qscale 变**」（体积差 3× 而 PSNR 恒定）—— 见到这种数就该怀疑量法。
   现在有工具：**`tools/psnr.py`** 按**帧号**比，并把偏移 `k=-K..K` 全扫一遍 ——
   峰值不在 `k=0` 就是没对齐，别拿那个数当判据。（差几帧能差出好几 dB：本仓吃过一次。）
   ⚠️ **跨容器**（源 `.wmv` 对产物 `.mp4`）时它**必然**错位，而且归零 PTS、`-fps_mode passthrough`
   都救不回来（实测：同一对文件它给 25.78 dB，而逐字节算出来是 49.76 dB —— 而且
   q=1 / q=2 / q=3 三档给出一模一样的 25.78，正是上面那个指纹）。**这种情况只能 dump 原始 YUV
   逐字节比**（两边 `-pix_fmt yuv420p -f rawvideo`，逐帧算 MSE）。
2. **同 qscale ≠ 同码率**：不带体积的 PSNR 对比会得出错误结论（第一版就是这么错的）。
3. **变帧率的源上 ffmpeg 会补帧**：帧数对不上就不能逐帧比（`ms/帧` 才是公平的速度口径）。
   ⚠️ **自己用 `ffmpeg` 倒参考帧时，`-fps_mode passthrough` 是必须的**：不带的话 rawvideo 那一路
   会按默认帧率**重采样**，VFR 源的帧序**整体错位**（实测在一份 VFR 样本上量出 19 dB 这种不可能的数）。
   它是**输出**选项 —— 写在 `-i` 前会直接报「不能把输出选项给输入」。这条踩过两次，第二次就是上面那张表。
4. **音频不能用 `-n` 截**：`v2v -n N` 会把音频一起截，ffmpeg 的 `-frames:v` 不会 —— 两边截在不同位置。
   要比短一点，就先把**同一份**干净 PCM 切好再喂给两个编码器，然后用 **`tools/snr.py`**
   （双向搜对齐 + 逐帧最差/中位）；它每次都把找到的偏移打出来，贴搜索窗边界会警告。
5. **对齐搜索别用暴力**：±20000 偏移 × 900 万样本在 Python 里是分钟级；FFT 互相关几秒就出。
6. **刚构建完的第一跑不能用来计时**：同一份二进制、同一份样本，第一跑比稳定态**慢 15~20%**
   （系统还在收尾、页缓存没热）。本仓 §2.1 那张表第一版就是拿「构建后立刻跑一次」的数写的，
   把 `.mp4` 那条算成 3.2×，实际是 2.76×。**同批次背靠背、三次取中位、丢掉第一次**。
7. **`ffmpeg` 默认多线程**：它的解码（VC-1 / H.264）默认开帧级多线程，不钉
   `-threads 1` 就会把「它用了 4 个核」算进「我们慢几倍」里 —— 实测 720p 上差 13%
   （4.99× vs 4.34×）。**比速度时两侧都要显式钉住线程数**。
8. **`ffmpeg` 的日志默认会折叠重复行**（`AV_LOG_SKIP_REPEATED`）：拿 `-debug` 日志当 oracle
   时，连续几十行一模一样的输出会被压成「Last message repeated N times」—— 日志成了**子集**，
   不报错，只让逐帧对账**整体错位**（VC-1 那条：3719 帧只剩 3525 行，看着像「第 10 帧起全错」）。
   要用 `-loglevel repeat+debug`。另外读入阶段的**探测解码器**也在打同一批日志，得按
   上下文地址把它那几行摘掉。

**这条差距已经翻过来了。** 把「按带选 sf/码本只看失真」换成**逐带率-失真分配**
（每带按 `失真 + λ·位数` 选，λ 从上一帧的答案出发搜）之后，中高码率**反超 ffmpeg**
（上表 +2 ～ +8 dB），实际码率也第一次**落在目标附近** —— 旧机制是系统性欠码约 3%，
等于预算没花完。还剩两块已知短板：`plan_group` 的**全局量化下界**（频谱动态范围大时
安静频带吃亏）、以及**按可闻度分配**（心理声学模型）—— 后者的两套机制（线性加权 /
阈值饱和）已经装进代码但**默认关**：本机没有 PEAQ/ViSQOL 这类听感 oracle，
收益无法本地判定，所以不拿 SNR 冒充当裁判。判据与细节在 `TODO.md`（本地）。

⚠️ **240×180 那档没测**：那份样本的首帧不是能解析的 I 帧，我们的解码器**不做错误隐藏**、
明确拒绝 —— 设计行为，不是回归。

### 7. 2026-11-06 复测：新语料 + R-D 曲线

上面 §2 / §6 是 2026-10-16 那版代码、320×240 前 200 帧的口径。之后编码器改过（MPEG 矩阵
量化成了默认、码率控制、trellis 等），所以用一套**新语料**重测了一遍：

- **语料**：6 段 3 秒（真内容 720p / 360p、合成运动 720p / 360p、近静止、满幅噪声），
  全部现造、不入库；噪声那档是故意加的 —— 它没有「该省的地方」，最容易暴露量化判决的短板。
- **工具**：`tools/ab_ffmpeg.py`（两侧单线程、同 qscale/GOP、无音频、PSNR 按帧号配对）。
- **报告**：`bench/ab-ffmpeg-20261106.md`，原始数据 `bench/ab-ffmpeg-20261106.tsv`
  与 `bench/ab-rd-20261106.tsv`。

**同 qscale 下**：慢 **1.98–4.34×**（720p 4.34×），体积 0.79–1.46×，PSNR −4.2 ~ +2.2 dB。

**同体积下**（把两条「体积 → PSNR」曲线拉到一起比，才是效率）：

| 语料 | 我们 − ffmpeg |
|---|---:|
| 真内容 720p | **−0.01 dB**（打平） |
| 真内容 360p | +0.48 dB |
| 合成 360p | +0.12 dB（曲线交叉） |
| 满幅噪声 | **−1.16 dB** |
| 近静止 | 不可用（ffmpeg 曲线不单调） |

**结论**：主战场（真内容）打平；唯一稳定落后的是**噪声**，而且已经定位到**帧内通路**
（噪声语料两侧其实都是全帧内），trellis 帮不上（它只作用于帧间块）。
⚠️ **同 qscale 的画质差 ≠ 编码效率差** —— §6 那句「别把同 q 变小读成变差」是同一个道理。

| **MP4** / ISOBMFF        | ✅   | ✅   | 解封装（`Mp4Demuxer`）：非分片、`moov` 在头或尾都行、`stco` 与 `co64` 都认、`ctts` 算进 PTS 并按 **PTS** 出样本。C ABI 通过 `v2v_probe` 和 `v2v_demux_*` 暴露 MP4，按包编号 seek 暂未支持。不做分片 MP4（`moof`）、`edts`/`elst` 编辑列表、加密（`encv`/`enca`）、H.265/AV1 的 sample entry |

### 视频编码

| 编码                       | 解码        | 编码        | 边界与原因                                                                        |
| ------------------------ | --------- | --------- | ---------------------------------------------------------------------------- |
| **MP43**（MS-MPEG-4 v3）   | ✅ I / P   | ✅ I / P   | 这是 `.wmv` 的主编码。解码有 AC 预测那条路（ffmpeg 编的流里 `ac_pred` 恒 0，靠翻位测试覆盖）                 |
| **MP42**（MS-MPEG-4 v2）   | ✅ I / P   | ❌         | 与 MP43 差在**三处表**（都不报错、只出错）：DC 走 H.263 那张 **512 项** VLC（符号以 **256** 为中心）、DC 缩放是 `ff_mpeg1_dc_scale_table`（**恒 8**）、运动矢量走 `H263_MV` + **±64 回绕**。自造样本 q=2/6/10/15 各 40 帧逐像素 0 差（`crates/msmpeg4/tests/v2.rs`）—— 低 qscale 分不出 DC 缩放表，必须带高档一起测 |
| **MP41**（MS-MPEG-4 v1）   | ❌         | ❌         | MB 层分支在代码里（H.263 的 MCBPC + cbpy），但 ffmpeg **没有 v1 编码器**、造不出对账样本 → 输入明确拒绝。等拿到真实 MP41 文件再验 |
| **WMV1**（WMV7）           | ✅ I / P   | ❌         | 与 MP43 共用 MB 层，分叉在帧头、扫描表、DC 预测/缩放表（见「状态」那行）。**不做错误隐藏** —— 首帧不是 I 帧的流直接报错，ffmpeg 会拿垃圾当参考硬解 |
| **WMV2**（WMV8）           | ✅ I/P + IntraX8 | ❌         | 帧头与 MB 层是另一套（`wmv2dec.c`）。比 WMV1 多：`parse_mb_skip`（4 种跳帧类型）、按 qscale 挑的 CBP 表、`mspel` 四抽头半像素 + `hshift`、**ABT**（4×8 / 8×4）、**环路滤波**、它自己那份 8×8 IDCT，以及 **IntraX8**（`j_type`，按 8×8 块走的内帧子解码器，WMV2 与 VC-1 共用 —— 见 `intrax8.rs`） |
| **WMV9 / VC-1**          | ✅ I / P   | ❌         | **ffmpeg 里根本没有 VC-1/wmv3 编码器**（只有解码器），想要 WMV9 得另找路子。解码侧 `v2v-vc1` 已走完整条链路（Main profile / 渐进 / I/P，真 1080p 样本逐帧逐像素 0 差）；缺 **B 帧 / 隔行 / Advanced profile**、overlap smoothing、多分辨率、重同步标记 —— 遇到明确报 `Unsupported`，不静默出错 |
| **MPEG-1**（`.mpg`） | ✅ I / P / B | ❌ | 走 `mpegps`（PS 容器）+ `mpeg12`。对 ffmpeg 逐帧比，容差 2（参考件是浮点 IDCT、我们是整数 IDCT）；真样本 50 帧全对 |
| **MPEG-2** | ✅ I / P / B（progressive + 隔行帧图） | ❌ | 含场 DCT、场运动、4:2:2 / 4:4:4 色度。**隔行流的 B 帧场预测还没收敛**（PSNR 47 dB，个别像素差 165）—— 测试里只报数不卡断言，见 TODO |
| **MPEG-4 Part 2**（`mp4v`） | ✅ I / P（H.263 与 **MPEG 矩阵**两种量化） | ✅ I / P   | 解码：AVI 里的 `FMP4` / `mp4v` / `DIVX` / `XVID` 都认，I / P 对 ffmpeg **逐像素 0 差**（`crates/mp4v/tests/ffmpeg_roundtrip.rs`，含独立来源的流）。`quant_type = 1`（MPEG 矩阵量化，含帧间**失配控制**）也已对齐 —— 所以「读回自己编的 `.mp4`」是通的。**不支持**：**自定义**量化矩阵（只做规范默认那对）、B / S 帧、4MV、`dquant`、隔行、GMC、数据分割、resync marker。编码默认走 **MPEG 型**（同体积下 SSIM 更高）+ 可选的**系数级 RD（trellis，默认关）** |
| **H.264 / AVC**          | ⭕ 硬件（macOS VideoToolbox） | ⭕ 硬件（FFI）：macOS VideoToolbox / Android MediaCodec | 软件侧不在范围内（LGPL 侧链不了 x264，见「许可证」）；硬件侧走 `crates/v2v-android`（见「FFI」一节）—— 真实样本实测 PSNR 42.45 dB（同码率反超 ffmpeg 的 mpeg4 1.7 dB） |

### 已知与 `ffmpeg` 的差异

| 项 | 对比口径 | 我们 vs `ffmpeg` |
| --- | --- | --- |
| **MP43 解码** | 整段真样本逐像素 | **最大差 0** |
| **VC-1 解码** | 真样本逐帧逐像素（`ffmpeg` 裸帧） | **最大差 0**（每帧位游标都不越过帧尾） |
| **WMA 解码** | 整轨对 ffmpeg 的 PCM，逐样本 | 最大差 **2**（v1）/ **3**（v2）—— 满量程 32768 |
| **音频直通** | 整条音轨 | **逐字节一致** |
| **ASF 封装** | ffmpeg 解我们写的 `.wmv` | 像素与我们的解码器**逐位一致** |
| **MP43 编码** | 不比 PSNR —— 比的是「两个解码器解得一样」 | 逐像素一致 |
| **`mp4v` 编码** | 同 qscale（真样本 PSNR），以及一档等码率 | 同 qscale **每一点都更高**（+0.03 ～ +1.17 dB，但体积 1.06 ～ 1.38×）；按**等体积**插值**基本打平**（±0.4 dB），等码率那一档 **43.48 vs 43.35 dB** |
| **AAC 编码 @128k** | 同目标码率，对源 PCM 比 SNR（先搜对齐） | **+2.1 dB**（另一段素材 +7.3） |
| **AAC 编码 @192k** | 同上 | **+3.1 dB**（另一段素材 +7.7） |
| **AAC 编码 @256k** | 同上 | **+3.1 dB**（另一段素材 +8.3） |
| **VC-1 解码速度** | 真样本全片（sample.wmv 720p 4138 帧）写 /dev/null，单线程同 `-idct 2` | **11.4 s vs 11.4 s（持平）**；产物 **5.7 GB md5 逐字节一致**（1080p 那份样本是 1.80×，见 §1） |
| **WMV→MP4 转码** | 真样本全片，同目标码率（4 Mbps + AAC 128k） | 体积差 **0.4%**；SSIM **0.9621 vs 0.9713**；PSNR **38.83 vs 40.77 dB**（差在 mpeg4 编码器，解码两侧逐字节一致）；音频 PSNR 对 WMA 真值都 ≈23 dB，**等价** |
| **AAC 时间轴** | 转码产物解码回 PCM | 我们的 MP4 **偏移 0**；`ffmpeg` 的带 **1024 帧 priming**（靠 edit list 补）—— 宿主直连播放时我们的免补偿 |
| **WMV→MP4（硬件 FFI）** | 同码率 4 Mbps，真实样本全片 | **SSIM 0.9820 / PSNR 42.45 dB**（软件栈 0.9621 / 38.83，ffmpeg mpeg4 0.9713 / 40.77）——质量与速度的短板都由硬件 H.264 吃掉，见「FFI」一节 |

**一句话**：解码侧是「逐像素 / 逐字节」（**速度** 720p 持平、1080p 差 1.80×）；编码侧 `mp4v` 等码率
**打平**、AAC 同码率**反超**、转码全栈体积与 `ffmpeg` 差 0.4% 而**编码质量差 1.9 dB**——
质量与速度的短板在设备上有出路：`crates/v2v-android` 的硬件路径（见「FFI」一节）。
剩下的已知短板在「状态」一节里那两段（`plan_group` 的量化下界、
按可闻度分配 / 心理声学模型）。

⚠️ **还有一个口径差异不是质量、是策略**：`--video-bitrate` 给目标码率时，我们**打满**它，
而 ffmpeg 的 mpeg4 会**欠**（实测目标 500k 它只花 370k）。所以「文件更大」在多数情况下
是**我们把码率用满了**，不是编码器效率低 —— 同码率比才是公平比法。

## 命令行

```bash
cargo run --release -p v2v-cli -- convert <输入.wmv>... -o <输出目录> [-q 6] [-g 250] [-n 100]
cargo run --release -p v2v-cli -- convert --mp4 <输入.wmv>... -o <输出目录> [-q 6] [-g 12] [--fps 25]
cargo run --release -p v2v-cli -- convert --mp4 --video-bitrate 500k <输入.wmv>... -o <输出目录>
cargo run --release -p v2v-cli -- convert --mp4 --trellis <输入.wmv>... -o <输出目录>

# 性能：打 TSV、存基线、对着基线卡回归（只卡比值，见 bench/README.md）
cargo run --release -p v2v-cli -- bench <样本.wmv>...
cargo run --release -p v2v-cli -- bench --baseline-dir bench/baseline <样本.wmv>...
cargo run --release -p v2v-cli -- bench --check bench/baseline/<机器指纹>.tsv <样本.wmv>...
```

`.mp4` 的音频默认 AAC：`--aac-bitrate 128000` 给目标码率，`--pcm` 退回未压缩 `sowt`，
`--no-ms` 关掉 M/S 立体声（只为对比测量）。
`--trellis` 打开帧间的**系数级 RD**（默认关）：逐系数在 `{L, L∓1}` 里挑「失真 + λ·位数」
最小的那个。**它只作用于帧间块**，而且实测现值偏保守（见 `bench/ab-ffmpeg-20261106.md`
的「追查」一节）—— 慢 5–9×，收益还没兑现。
`--threads N` 给并行度（默认 1）：视频按 **GOP** 并行，音频按**帧**并行（批内连续分块）与
**声道**并行；线程数都封顶到可用并行度。
**并行度上限就是 GOP 数** —— `-g 250` 配 `--threads 8` 是白给（300 帧只有 2 个 GOP）。

产物与单线程的关系**两条路不一样**：

- **`.wmv`（MP43）：逐字节相同。** 编码器没有跨 GOP 的状态，所以每块起新编码器编出来的字节
  完全一样，包排布也一样（结果按 GOP 序号归位后与音频按 pts 合并 = 串行读到的顺序）。
  有测试钉着（`crates/v2v-cli/tests/convert.rs::parallel_gop_encoding_is_byte_identical`）。
- **`.mp4`（mp4v）：不完全相同。** 每个 GOP 的第一个 P 帧少一个搜索起点、码控从头收敛 ——
  质量与体积在同一档，但不是同一个文件。

**输入编码**：`MP42`、`MP43`、`WMV1`（WMV7）、`WMV2`（WMV8）、**`WMV3`（VC-1）**，
以及 AVI 里的 `mp4v`（`FMP4` / `DIVX` / `XVID`）—— 其余 MS-MPEG-4 版本会**明确报错
且不留输出文件**，不会静默按错的语法解（MP41 没有可对账的样本，所以拒绝而不是猜）。
`--video-bitrate` 只对 `.mp4` 有效：给了它就按目标码率**逐帧调 qscale**（`-q` 退化成起步值），
转完会报**实际**码率；不传就还是按固定的 `-q` 编。

批量：一个输入失败不影响其他。默认（`.wmv`）转完会把输出**解码回来**与源帧比 PSNR；  
`--mp4` 不做这个校验 —— 那条路的正确性由 `crates/mp4v/tests/ffmpeg_roundtrip.rs`  
（`mp4v` 编 → `ffmpeg` 解，逐像素 0 差）钉着。

输入容器按**魔数**自动认（`ASF` / `AVI` / **`MP4`**，不看扩展名）；  
别的容器 / codec 会明确报「不支持」，不静默跳过。

## 路线与分支策略

这个项目绕不开一个两难：**要么保 FFI / 结构清晰**（强调可复用性、流畅性、可监督性——  
每一段清晰可查、可单独替换、能当库嵌进别的应用），**要么追齐 ffmpeg 的性能**  
（SIMD / 手写内核 / 定点化，复杂度与可维护性代价都大）。

**我们的取舍：在 Android 上拿到最完整构建是第一优先级，性能暂时让路。** 落到分支上：

- **`main` = 可扩展性**。新能力、新格式、结构改良进 main；性能敏感的实现  
  允许「正确但慢」——先把语义钉对，再谈快。
- **性能改动进按类型归类的专门分支**（同类型改动进同一分支，便于跟进与随时改动）：  
  `perf/encode`（编码提速）、`perf/decode`（解码提速）、`perf/tables`（码表改良）。
- 性能分支**保持短命**：定期 rebase、验证过（输出字节不变）就合回 main——  
  永远不合并的性能优化等于没有。

**实测的位置**：见下面「与 ffmpeg 的全面对表」——**编码慢、解码接近**，
音频那条链已经打平。曾经在**一份小样本**上量到过「端到端只慢 1.33 倍」，
那是短样本上启动开销与音频占比把视频编码那一段盖住了的产物，**不能代表一般素材**。

**五笔大的都是「本该便宜却没便宜」**（每一笔的判据都是**产物 MD5 不变**，
除非注明；每笔前后的数都记在 `TODO.md`）：

① **变换是 O(N²)**：AAC 的前向 MDCT 与 WMA 的 IMDCT 原来都逐点调 `cos()`。
AAC 那半先治（`预旋转 → 2N 点 FFT → 后旋转`：单编 20 秒 13.85 → 2.81 s，**4.9×**）；
WMA 这半走同一条路（`n` 点 DCT-IV 折成三段对称 + 一次 `2n` 点 FFT）：
**WMA 解码 1.73 → 0.10 s（约 17×）**。FFT 住在共享内核（现在是 `v2v-kernel`，当时还在
`v2v-msmpeg4` 里），aac 与 wma 调同一份。
（WMA 这条是**唯一**不是逐字节的：PCM 里 550/716800 个样本差 ±1 LSB —— 旧版逐项舍 f32、
新版 f64 累完收一次，**新版更准**。）
后来这个内核又单独治过一轮：**相邻两级 radix-2 融合进一趟 + 位反转改查表**，
n=128…2048 上 **×1.36~1.41**，而浮点运算的次数与顺序一字未动 —— 产物逐位相同。

② **MP43 解码的运动补偿每块都在做无用功**：`edge_emu` 每块一次 `vec!` 分配 + 逐像素
两次 `clamp`，`put_pixels` 靠逐像素闭包算地址。改成栈 scratch + 三段切片 + 相位分开写。

③ **运动估计把同一个候选反复求值**：菱形每走一步、三个起点各走一遍、±2 补搜、半像素
细化 —— 而 SAD 只取决于候选与参考帧。加一张**直接映射 + 代号**的记忆表（256 槽，
每宏块换一代、不清表）：**视频路径 ×1.30**。

④ **两个编码器的运动估计各写了一份**：MP43 那半每个候选都「先 `mc_luma16` 搬进缓冲
再求和」（两趟内存流量），mp4v 那半早就融合成一趟 —— 合成共享内核里的 `sad_luma16`；
顺带去掉 MP43 ME 里那个占了整条 `.wmv` 链路 **12%** 的 `HashSet` 去重：
**`.wmv` 路径 ×1.23**。

⑤ **AAC 的失真评估算了 11 次、还白算位数**：11 本码本只有 **6 个不同的封顶值**
（1,1,2,2,4,4,7,7,12,12,16），而失真只取决于封顶值 → 算 6 次就够；「位数」那一半本来
就是白算的（`band_cost` 只看失真，位数由 `write_band` 写位流时自己算）：**AAC ×1.7**。

**外加一个真 bug**：AAC 的代价模型里 escape 那一路的反量化漏了符号（位流没错 ——
escape 码本无符号、符号位单独发）。负系数的误差于是被估成 `(|c|+rec)²` 量级，编码器
系统性避开 escape、把大系数逼去撞 `maxval ≤ 16` 的普通码本。修好后 **256k 上 +0.289 dB**
（64k / 128k 几乎不变 —— 低码率下 sf 预算本来就主导）。

**下一个靶子**：视频那 81% —— 运动估计（13%）、共享 DCT、位写入与封装；
再往前就是**分块并行**（按 I 帧切、固定 qscale 下逐字节不变）这一轴。
加速的路子（哪些做过了、哪些试过又撤了、每步前后量到的数）都在 `TODO.md`（本地）里。

## 许可证

**分两种**：

| 范围 | 许可证 |
|---|---|
| `crates/{tables, msmpeg4, vc1, aac, wma, mp4v, mpeg12, mp3}` | **LGPL-2.1-or-later**（[LICENSE](LICENSE)） |
| 其余带 `v2v-` 前缀的 crate（含 `v2v-audio-ffi`） | **MIT**（[LICENSE-MIT](LICENSE-MIT)） |

分界的**唯一依据是码表**：**全部码表都在 `crates/tables`**（从 FFmpeg 数据文件读出的
VLC / 反量化 / Huffman 表，同为 LGPL-2.1-or-later），另外七个编解码器 crate 依赖它。
